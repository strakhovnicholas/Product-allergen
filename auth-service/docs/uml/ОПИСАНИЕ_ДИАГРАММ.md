# Описание UML-диаграмм микросервиса auth-service

> Документ является развёрнутым пояснением к диаграммам, расположенным в каталоге
> `auth-service/docs/uml/plantuml/`. Текст рассчитан на включение в раздел
> «Проектирование» дипломной работы. Каждый подраздел соответствует одному из
> файлов `.puml` и завершается указанием места вставки рисунка с подписью.

## Общая характеристика микросервиса auth-service

**auth-service** — выделенный микросервис аутентификации и управления
JSON Web Token‑ами (JWT). Сервис изолирует контур безопасности от прикладных
сервисов (`user-service`, `analytics-service`) и реализует следующие
функции:

- регистрация новой учётной записи (логин — адрес электронной почты, пароль
  хранится в виде BCrypt‑хеша);
- проверка учётных данных при входе и выдача пары токенов: короткоживущего
  **access‑токена** (по умолчанию 15 минут) и долгоживущего **refresh‑токена**
  (7 суток);
- обновление access‑токена по действующему refresh‑токену без повторного
  ввода пароля;
- инвалидация refresh‑токена при выходе из системы.

Сервис не предоставляет публичных endpoint‑ов: все вызовы поступают через
**gateway-service** (Spring Cloud Gateway), который маршрутизирует префикс
`/auth/**` непосредственно в auth-service без проверки JWT.

Технологический стек:

| Слой | Решение |
|---|---|
| Язык / платформа | Java 17, Spring Boot 3.2 |
| Безопасность | Spring Security 6, BCrypt, `io.jsonwebtoken` 0.11 (JJWT) |
| Персистентность учётных записей | PostgreSQL 16 (схема `allergen_pg`, таблица `users`) |
| Хранилище refresh‑токенов | Redis 7 (kv‑пары `<token> → email` с TTL) |
| Документирование API | springdoc‑openapi (Swagger UI) |
| Контейнеризация | Docker, Docker Compose |

## 2.X.1. Диаграмма вариантов использования

**Файл:** `auth-service/docs/uml/plantuml/01-use-case.puml`.

### 2.X.1.1. Назначение диаграммы

Диаграмма вариантов использования отражает поведенческие контракты, которые
auth-service обязан выполнять для внешних акторов. Цель — зафиксировать
**границы ответственности** сервиса (всё, что относится к управлению
учётной записью и сессиями, и **только** оно) и обозначить полный набор
сценариев, реализуемых в публичном API.

### 2.X.1.2. Акторы

В диаграмме выделены два актора:

1. **Клиент** (мобильное или веб‑приложение конечного пользователя) — инициатор
   всех основных сценариев. Связь физически осуществляется через шлюз
   (`gateway-service`), однако с точки зрения системы поведение
   соответствует прямой роли «пользователь системы».
2. **API Gateway** — технический актор, выступающий посредником между
   клиентом и auth-service. Включён в диаграмму для тех сценариев, в которых
   шлюз является непосредственным инициатором запроса (например, при
   валидации токенов в сценарии входа и обновления). Включение технического
   актора отделяет роли «бизнес‑инициатора» (Клиент) и «технического
   инициатора» (Gateway).

### 2.X.1.3. Основные прецеденты

**UC‑01 Регистрация (`POST /auth/register`).** Прецедент инициируется
Клиентом при первом обращении к системе. Входные данные — DTO `RegisterRequest`
(email + пароль). Система проверяет, что email не занят, хеширует пароль
алгоритмом BCrypt с автоматически сгенерированной солью, сохраняет новую
запись в таблицу `users` и в одной транзакции возвращает пару JWT.
Постусловие: в PostgreSQL появляется запись, в Redis — refresh‑токен.

**UC‑02 Вход (`POST /auth/login`).** Прецедент инициируется Клиентом для
получения новой пары токенов. Входные данные — `LoginRequest`. Система
делегирует проверку пароля Spring Security‑шному
`AuthenticationManager`, который через `UserDetailsService` извлекает
учётную запись из PostgreSQL и сравнивает хеш пароля. При успехе **все ранее
выданные refresh‑токены** пользователя отзываются (явный выход «со всех
устройств» при повторном входе) и в Redis записывается новый. На выход —
пара токенов.

**UC‑03 Выход (`POST /auth/logout`).** Прецедент завершает сессию по
переданному refresh‑токену. Сервис удаляет из Redis сам токен и его упоминание
в множестве `user_tokens:<email>`. Завершение возможно даже при истёкшем
access‑токене — это особенность дизайна: logout требует только знания
refresh‑токена.

**UC‑04 Обновление токенов (`POST /auth/refresh`).** Прецедент инициируется
при истечении access‑токена. Сервис проверяет подпись и срок действия
refresh, его наличие в Redis (т. е. факт активности), извлекает email и
выдаёт **новый access‑токен**, сохраняя прежний refresh. Такой подход
называется *sliding access*: пользователь продолжает работать, пока активен
refresh; replay‑атака коротко‑живущим access‑токеном ограничена по времени.

### 2.X.1.4. Вспомогательные (включённые) прецеденты

Чтобы избежать дублирования логики в основных UC, в диаграмму вынесены три
**включённых прецедента** (отношение `«include»`):

**Валидация входных данных.** Поведение Spring Bean Validation, применяемое
ко всем DTO (`@Valid` в контроллере). При нарушении правил
(`@Email`, `@NotBlank`, `@Size(min=8)`) выбрасывается
`MethodArgumentNotValidException`, преобразуемая `GlobalExceptionHandler`‑ом
в HTTP 400. Связан с UC‑01, UC‑02, UC‑03, UC‑04.

**Выдача JWT.** Поведение `JwtService.generateAccessToken(email, id)` и
`JwtService.generateRefreshToken(email)`. Включается в UC‑01, UC‑02, UC‑04
(в UC‑04 — только access). В access‑токен попадают `subject = email`,
claim `id` (UUID пользователя) и claim `type = "access"`; в
refresh — `subject = email`, claim `type = "refresh"`. Подпись — HMAC SHA‑256
на секрете из `${JWT_SECRET}`.

**Хранение refresh в Redis.** Поведение `RefreshTokenService`. Включается
в UC‑01, UC‑02, UC‑03, UC‑04. Технически — хранение двух ключей:
`<token> → <email>` с TTL 7 суток и множества `user_tokens:<email>` со
списком всех активных токенов пользователя (для быстрой инвалидации «со
всех устройств»).

### 2.X.1.5. Документирование отношений

- UC‑01, UC‑02, UC‑03, UC‑04 ⟹ **«Валидация входных данных»** — тип `include`,
  поскольку без проверки полей входного DTO ни один сценарий не может быть
  корректно выполнен.
- UC‑01, UC‑02, UC‑04 ⟹ **«Выдача JWT»** — тип `include`: выдача токенов
  является обязательной частью успешного завершения каждого из этих
  сценариев.
- UC‑01, UC‑02, UC‑03, UC‑04 ⟹ **«Хранение refresh в Redis»** — тип `include`:
  refresh‑токены не существуют в коде сервиса вне Redis, поэтому любая
  операция с ними автоматически использует это поведение.

> *Подпись:* «Рисунок — Диаграмма вариантов использования микросервиса auth-service».

## 2.X.2. Диаграмма последовательности — UC‑02 Вход

**Файл:** `auth-service/docs/uml/plantuml/02-sequence-login.puml`.

### 2.X.2.1. Назначение и линии жизни

Диаграмма последовательности показывает упорядоченный во времени обмен
сообщениями между объектами при выполнении прецедента UC‑02. Линии жизни
(participant‑ы):

| Объект | Стереотип / роль | Класс / компонент |
|---|---|---|
| Клиент | actor | внешнее приложение |
| AuthController | `<<boundary>>` | `controller.AuthController` |
| AuthService | `<<control>>` | `service.auth.AuthService` |
| AuthenticationManager | `<<control>>` | Spring Security |
| UserRepository | `<<control>>` | `repository.UserRepository` (Spring Data JPA) |
| JwtService | `<<control>>` | `security.JwtService` |
| RefreshTokenService | `<<control>>` | `service.storing.RefreshTokenService` |
| PostgreSQL | `<<entity>>` | внешнее хранилище |
| Redis | `<<entity>>` | внешнее хранилище |

### 2.X.2.2. Последовательность сообщений

1. **Клиент → AuthController : `POST /auth/login`** — HTTP‑запрос с
   `Content-Type: application/json` и телом `{ "email": ..., "password": ... }`.
   В Spring сначала выполняется десериализация JSON в `LoginRequest` (record),
   затем Bean Validation: при нарушении правил аннотации возвращается HTTP 400
   (см. вспомогательный UC «Валидация»).
2. **AuthController → AuthService : `login(request)`** — делегирование без
   преобразований; контроллер логирует факт запроса.
3. **AuthService → AuthenticationManager : `authenticate(email, password)`** —
   передача `UsernamePasswordAuthenticationToken`. Внутри Spring Security
   вызывается `UserDetailsService`, который через `UserRepository`
   достаёт `User` из БД.
4. **UserRepository → PostgreSQL : `SELECT * FROM users WHERE email = ?`** —
   запрос по уникальному индексу. Возвращается одна строка или пусто.
5. **PostgreSQL → UserRepository → AuthenticationManager** — возврат
   `UserDetails` (роль: класс `entity.User`, реализующий `UserDetails`).
   `AuthenticationManager` сравнивает полученный BCrypt‑хеш с хешем
   введённого пароля.
6. **Альтернативный поток (`alt`) — неверные учётные данные.** Spring бросает
   `BadCredentialsException`. `AuthService` перехватывает любое исключение
   из `authenticate(...)` и заменяет его доменным
   `InvalidCredentialsException`. `GlobalExceptionHandler` отображает его в
   HTTP 401 с телом `ApiErrorResponse{message, status}`. Контроллер
   возвращает 401 клиенту. Сценарий завершается.
7. **Основной поток — успешная аутентификация.** AuthenticationManager
   подтверждает корректность пароля.
8. **AuthService → UserRepository → PostgreSQL : `findByEmail(email)`** —
   повторный запрос, чтобы получить **доменную сущность** `User` (не
   `UserDetails`‑адаптер) и иметь доступ к UUID пользователя.
9. **AuthService → JwtService : `generateAccessToken(email, id)`** — выдача
   нового access‑токена со claim‑ами `subject=email`, `id=<UUID>`,
   `type=access`. Срок — 15 минут (`jwt.access.expiration`).
10. **AuthService → JwtService : `generateRefreshToken(email)`** — выдача
    refresh со claim‑ами `subject=email`, `type=refresh`. Срок — 7 суток
    (`jwt.refresh.expiration`).
11. **AuthService → RefreshTokenService : `revokeOldTokensByEmail(email)`** —
    инвалидация всех ранее выданных refresh‑токенов того же пользователя.
    Реализация: чтение множества `user_tokens:<email>`, удаление каждого
    ключа‑токена, удаление самого множества. Эта мера превращает повторный
    вход в **глобальный logout со всех устройств**, что повышает
    защищённость в сценарии компрометации refresh‑токена.
12. **AuthService → RefreshTokenService : `saveRefreshToken(token, email)`** —
    запись новой пары `<token> → email` в Redis с TTL 7 суток и добавление
    токена в множество `user_tokens:<email>` (тоже с TTL).
13. **AuthService → AuthController → Клиент : `AuthResponse{accessToken, refreshToken}`** —
    возврат сериализованного DTO с HTTP 200.

### 2.X.2.3. Транзакционные границы и гарантии

Метод `AuthService.login` помечен `@Transactional`. Транзакция распространяется
на чтение `User` из PostgreSQL и не охватывает работу с Redis (это разные
ресурс‑менеджеры). При сбое записи в Redis уже выданный access‑токен
останется в ответе, однако его срок действия (15 минут) ограничивает
последствия. На уровне `RefreshTokenService` операции `saveRefreshToken` и
`revokeOldTokensByEmail` атомарны по отдельности, но не объединены в
кросс‑ресурсную транзакцию — это сознательное упрощение, типичное для
микросервисной архитектуры (см. концепцию *eventual consistency*).

> *Подпись:* «Рисунок — Диаграмма последовательности прецедента UC‑02 “Вход”».

## 2.X.3. Диаграмма последовательности — UC‑01 Регистрация

**Файл:** `auth-service/docs/uml/plantuml/03-sequence-register.puml`.

### 2.X.3.1. Линии жизни и краткое описание

Состав участников близок к UC‑02, за исключением `AuthenticationManager`:
проверка пароля не нужна, так как пользователь ещё не существует. Появляется
участник **PasswordEncoder** (`BCryptPasswordEncoder`), отвечающий за
хеширование.

### 2.X.3.2. Последовательность сообщений

1. **Клиент → AuthController : `POST /auth/register`** с телом
   `RegisterRequest{ email, password }`. Bean Validation проверяет формат
   email и минимальную длину пароля (`@Size(min=8)`); при нарушении —
   HTTP 400.
2. **AuthController → AuthService : `register(request)`** — делегирование.
3. **AuthService → UserRepository → PostgreSQL : `existsByEmail(email)`** —
   запрос `SELECT EXISTS(SELECT 1 FROM users WHERE email = ?)`.
4. **Альтернатива 1 — email уже занят.** `UserRepository` возвращает `true`,
   `AuthService` бросает `UserAlreadyExistsException`,
   `GlobalExceptionHandler` отображает его в HTTP 409 (Conflict). Сценарий
   завершается.
5. **Основной поток.** `existsByEmail` возвращает `false`.
6. **AuthService → PasswordEncoder : `encode(rawPassword)`** — хеширование
   пароля BCrypt со стандартной стоимостью 10 (Spring default).
   На выходе — строка вида `$2a$10$...`.
7. **AuthService → UserRepository → PostgreSQL : `INSERT INTO users (...)`** —
   сохранение новой записи. Поля `id` (UUID), `created_at`, `updated_at`,
   `is_active = true` устанавливаются в hook‑ах `@PrePersist`.
8. **AuthService → JwtService → AuthService : `generateAccessToken`,
   `generateRefreshToken`** — выдача пары JWT (см. UC‑02, шаги 9–10).
9. **AuthService → RefreshTokenService → Redis : `saveRefreshToken`** —
   запись токена и его включение в множество `user_tokens:<email>`.
10. **AuthService → AuthController → Клиент : `AuthResponse`** — возврат
    HTTP 200.

### 2.X.3.3. Особенности транзакции

Метод `register` помечен `@Transactional`, что гарантирует откат INSERT
при последующей ошибке в той же транзакции. Однако вызовы Redis и
`JwtService` не участвуют в транзакции БД — это намеренное проектное
решение: при сбое Redis запись о пользователе уже создана, и клиент сможет
повторно войти через UC‑02. Альтернативой был бы распределённый протокол
2PC, отвергнутый из соображений сложности и снижения доступности.

> *Подпись:* «Рисунок — Диаграмма последовательности прецедента UC‑01 “Регистрация”».

## 2.X.4. Диаграмма последовательности — UC‑03 Выход

**Файл:** `auth-service/docs/uml/plantuml/04-sequence-logout.puml`.

### 2.X.4.1. Назначение

Прецедент UC‑03 является **stateless‑операцией без чтения PostgreSQL**:
auth-service не хранит сессии в реляционной БД, поэтому выход сводится к
удалению ключа из Redis.

### 2.X.4.2. Последовательность сообщений

1. **Клиент → AuthController : `POST /auth/logout`** с телом
   `LogoutRequest{ refreshToken }`. Bean Validation проверяет, что поле не
   пустое.
2. **AuthController → AuthService : `logout(refreshToken)`** — делегирование.
3. **AuthService** проверяет, что параметр не `null` и не blank. В противном
   случае метод тихо завершается — это сделано для **идемпотентности**: при
   повторном выходе или при logout уже истёкшего токена сервис не должен
   возвращать ошибку клиенту.
4. **AuthService → RefreshTokenService : `revokeToken(refreshToken)`**.
5. **RefreshTokenService → Redis : `GET <token>`** — извлечение email,
   привязанного к токену.
6. **Альтернатива — токена нет в Redis.** Возвращается `null`, метод
   `revokeToken` завершается без ошибки. Поведение идемпотентно.
7. **Основной поток.** Если email получен:
   1. **RefreshTokenService → Redis : `SREM user_tokens:<email> <token>`** —
      удаление токена из множества активных токенов пользователя.
   2. **RefreshTokenService → Redis : `DEL <token>`** — удаление основной
      пары ключ‑значение.
8. **AuthService → AuthController → Клиент** — возврат строкового тела
   `"Выход выполнен успешно"` с HTTP 200.

### 2.X.4.3. Замечание

Logout **не отзывает access‑токен**: формально он остаётся валидным до
истечения срока (≤ 15 минут). Это типичный компромисс в JWT‑based
архитектурах: «настоящий» отзыв access потребовал бы проверки чёрного
списка при каждой операции, что лишает JWT преимуществ stateless‑модели.
Защита от компрометации обеспечивается коротким TTL access‑токена.

> **ВСТАВИТЬ РИСУНОК.** Файл `04-sequence-logout.puml`.  
> *Подпись:* «Рисунок — Диаграмма последовательности прецедента UC‑03 “Выход”».

## 2.X.5. Диаграмма последовательности — UC‑04 Обновление токенов

**Файл:** `auth-service/docs/uml/plantuml/05-sequence-refresh.puml`.

### 2.X.5.1. Назначение

Прецедент позволяет получать новый access‑токен, не предъявляя пароль.
Условия выдачи: refresh имеет корректную HMAC‑подпись, не истёк и **физически
присутствует в Redis** (т. е. не отозван).

### 2.X.5.2. Последовательность сообщений

1. **Клиент → AuthController : `POST /auth/refresh`** с телом
   `RefreshRequest{ refreshToken }`.
2. **AuthController → AuthService : `refresh(refreshToken)`**.
3. **AuthService → JwtService : `validateToken(token, "refresh")`**. Проверки:
   - целостность HMAC‑подписи (`io.jsonwebtoken.Jwts.parserBuilder(...).parseClaimsJws`);
   - совпадение claim `type` со значением `"refresh"` (защита от
     попытки подмены access‑токеном);
   - истечение срока действия по `claims.getExpiration()`.
4. **Альтернатива 1 — токен не прошёл криптографическую проверку.**
   `validateToken` возвращает `false`, `AuthService` бросает
   `InvalidRefreshTokenException` (HTTP 401).
5. **AuthService → RefreshTokenService : `isValid(token)`** —
   `redisTemplate.hasKey(token)`.
6. **Альтернатива 2 — токена нет в Redis.** Подпись валидна, но токен был
   отозван (logout, повторный login) или истёк по TTL Redis (рассинхронизация
   с JWT exp). Сервис бросает `InvalidRefreshTokenException` (HTTP 401).
   Этот двойной контроль (подпись + физическое наличие) является ключевой
   мерой защиты от replay‑атак.
7. **Основной поток.** **RefreshTokenService → Redis : `GET <token>`** —
   получение email.
8. **AuthService → UserRepository → PostgreSQL : `findByEmail(email)`** —
   проверка, что учётная запись существует и не была удалена администратором.
9. **AuthService → JwtService : `generateAccessToken(email, id)`** —
   выпуск **только access‑токена**; сам refresh остаётся прежним и продолжает
   действовать до истечения 7 суток.
10. **AuthService → AuthController → Клиент : `AuthResponse{ newAccess, oldRefresh }`**
    с HTTP 200.

### 2.X.5.3. Стратегия «sliding access»

При данной стратегии срок действия refresh не продлевается при обновлении.
Альтернативные стратегии (sliding refresh, sliding session) требуют либо
дополнительной записи в Redis, либо повышенного риска неограниченного
времени жизни сессии. Принятая стратегия даёт фиксированную верхнюю границу
длительности сессии (7 суток).

## 2.X.6. Диаграмма классов

**Файл:** `auth-service/docs/uml/plantuml/06-class.puml`.

### 2.X.6.1. Назначение диаграммы

Диаграмма классов представляет статическую структуру кода: классы и
интерфейсы, их атрибуты и операции, а также отношения зависимостей и
ассоциаций. Для удобства восприятия классы сгруппированы в **семь логических
пакетов**, отражающих архитектурные слои.

### 2.X.6.2. Пакет `controller`

Содержит **REST‑контроллер**, выступающий граничным компонентом
(`<<boundary>>` в терминах ICONIX).

**`AuthController`** — единственный REST‑контроллер сервиса, аннотирован
`@RestController` и `@RequestMapping("/auth")`. Объявляет четыре endpoint‑а:

```
+ login(LoginRequest)        → ResponseEntity<AuthResponse>     [POST /login]
+ register(RegisterRequest)  → ResponseEntity<AuthResponse>     [POST /register]
+ logout(LogoutRequest)      → ResponseEntity<String>           [POST /logout]
+ refresh(RefreshRequest)    → ResponseEntity<AuthResponse>     [POST /refresh]
```

Контроллер делегирует выполнение бизнес‑логики единственному полю
`authService` (ассоциация `AuthController → AuthService`). Сам контроллер
**не работает с БД и Redis напрямую** — это сознательное разделение
обязанностей.

### 2.X.6.3. Пакет `service`

Содержит классы прикладного слоя (`<<control>>`).

**`AuthService`** — координатор. Знает обо всех downstream‑сервисах
(`UserRepository`, `PasswordEncoder`, `AuthenticationManager`,
`JwtService`, `RefreshTokenService`). Содержит четыре основных публичных
метода — по числу прецедентов:

| Метод | Возвращает | Назначение |
|---|---|---|
| `register(RegisterRequest)` | `AuthResponse` | реализация UC‑01 |
| `login(LoginRequest)` | `AuthResponse` | реализация UC‑02 |
| `logout(String)` | `void` | реализация UC‑03 |
| `refresh(String)` | `AuthResponse` | реализация UC‑04 |

Методы `register` и `login` помечены `@Transactional` для целостности записи
в PostgreSQL.

**`RefreshTokenService`** — узкоспециализированный класс работы с Redis.
Атрибуты: `redisTemplate : RedisTemplate<String, String>`, константа
`REFRESH_TOKEN_TTL = Duration.ofDays(7)`. Методы: `saveRefreshToken`,
`revokeOldTokensByEmail`, `isValid`, `getEmail`, `revokeToken`. Класс
инкапсулирует **схему хранения refresh‑токенов** (пара ключей: сам токен
и `user_tokens:<email>` SET); вышестоящий код знает только методы.

### 2.X.6.4. Пакет `security`

Содержит классы, относящиеся к Spring Security и JWT.

**`JwtService`** — выпуск и проверка JWT‑токенов. Использует библиотеку JJWT.
Внутренний ключ `SECRET_KEY : Key` инициализируется в `@PostConstruct`
из значения свойства `${jwt.secret}` (HMAC SHA‑256). Публичные методы:
`generateAccessToken(email, id)`, `generateRefreshToken(email)`,
`validateToken(token, expectedType)`, `extractEmail(token)`, `extractType(token)`.

**`SecurityConfig`** — Spring‑конфигурация (бины
`PasswordEncoder`, `AuthenticationManager`, `SecurityFilterChain`,
`UserDetailsService`). Политика сессий — `STATELESS`, CSRF отключён
(для REST‑API JWT). Поскольку проверка JWT на входе выполняется
**на gateway**, в самом auth-service ограничений на пути нет
(`anyRequest().permitAll()`).

### 2.X.6.5. Пакет `persistence`

**Интерфейс `UserRepository extends JpaRepository<User, UUID>`** —
Spring Data JPA‑репозиторий. Объявляет два специализированных метода:
`Optional<User> findByEmail(String email)` и
`boolean existsByEmail(String email)`. Реализация генерируется фреймворком.

**Класс `User`** — JPA‑сущность (`@Entity`, `@Table(name="users")`),
реализующая `org.springframework.security.core.userdetails.UserDetails`
(чтобы `UserDetailsService` мог вернуть сущность напрямую). Атрибуты:

- `id : UUID` — первичный ключ, `@GeneratedValue(strategy=UUID)`;
- `email : String` — уникальный (`@Column(unique=true)`), валидируется
  на формат и непустоту;
- `password : String` — хешированный BCrypt;
- `isActive : boolean`;
- `createdAt`, `updatedAt : LocalDateTime` — заполняются в
  `@PrePersist`/`@PreUpdate`.

### 2.X.6.6. Пакет `dto`

Содержит DTO для входа/выхода (все DTO реализованы как Java `record`):

- `LoginRequest(String email, String password)` — c
  `@Email`, `@NotBlank`;
- `RegisterRequest` — те же поля, `@Size(min=8)` на пароль;
- `LogoutRequest(String refreshToken)` — `@NotBlank`;
- `RefreshRequest(String refreshToken)` — `@NotBlank`;
- `AuthResponse(String accessToken, String refreshToken)` — ответ;
- `ApiErrorResponse(String message, int status)` — единый формат ошибок.

DTO‑слой намеренно отделён от сущности `User`: это предотвращает
непреднамеренную сериализацию хеша пароля в ответы API.

### 2.X.6.7. Пакет `exception`

Содержит доменные исключения: `InvalidCredentialsException` (HTTP 401),
`UserAlreadyExistsException` (HTTP 409),
`InvalidRefreshTokenException` (HTTP 401),
`UserNotFoundException` (HTTP 404). Все они перехватываются в
**`GlobalExceptionHandler`** (`@RestControllerAdvice`), который
преобразует исключение в `ApiErrorResponse` с нужным HTTP‑кодом. Такой
паттерн централизует обработку ошибок и избавляет контроллер от
блоков `try/catch`.

### 2.X.6.8. Пакет `config`

**`OpenApiConfig`** — конфигурация springdoc‑openapi. Регистрирует
информацию об API (название, версия) и схему авторизации в Swagger UI.

### 2.X.6.9. Сводная таблица отношений

| Тип | Источник | Цель | Семантика |
|---|---|---|---|
| Ассоциация | `AuthController` | `AuthService` | внедрение зависимости |
| Ассоциация | `AuthService` | `UserRepository` | чтение/запись `User` |
| Ассоциация | `AuthService` | `JwtService` | выпуск токенов |
| Ассоциация | `AuthService` | `RefreshTokenService` | работа с Redis |
| Зависимость | `UserRepository` | `User` | возврат типа |
| Зависимость | `AuthController` | DTO (`Login/Register/...Request`, `AuthResponse`) | приём/возврат |
| Зависимость | `GlobalExceptionHandler` | `ApiErrorResponse` | формирование ответа |

> **ВСТАВИТЬ РИСУНОК.** Файл `06-class.puml`.  
> *Подпись:* «Рисунок — Диаграмма классов микросервиса auth-service».

## 2.X.7. Диаграмма компонентов

**Файл:** `auth-service/docs/uml/plantuml/07-component.puml`.

### 2.X.7.1. Назначение

Диаграмма компонентов отображает развёртываемые **программные модули**
сервиса и их связи на уровне абстракции выше, чем у диаграммы классов.
Она показывает **что** обращается **к чему**, без указания методов и
сигнатур.

### 2.X.7.2. Состав компонентов

- **AuthController** — точка входа HTTP, экспонирует интерфейс `HTTP/JSON`
  (REST API под префиксом `/auth/**`).
- **AuthService** — компонент прикладной логики, координирующий все
  операции.
- **JwtService** — компонент выпуска и проверки JWT.
- **RefreshTokenService** — компонент работы с Redis.
- **UserRepository** — компонент доступа к PostgreSQL (Spring Data JPA).
- **SecurityConfig** — конфигурирующий компонент (Spring beans).
- **GlobalExceptionHandler** — компонент централизованной обработки
  ошибок.

### 2.X.7.3. Внешние компоненты

- **PostgreSQL `(users)`** — реляционная база, размещаемая в отдельном
  Docker‑контейнере, доступна по TCP/JDBC.
- **Redis `(refresh)`** — in‑memory KV‑хранилище, доступно по TCP.

### 2.X.7.4. Связи между компонентами

Ключевые направления стрелок:

- HTTP/JSON ⟶ AuthController — внешний интерфейс;
- AuthController ⟶ AuthService — все запросы делегируются дальше;
- AuthService ⟶ JwtService, RefreshTokenService, UserRepository —
  координирование;
- SecurityConfig ⤳ AuthService (отношение «использования», `<<use>>`) —
  конфигурация бинов;
- GlobalExceptionHandler ⤳ AuthController — перехват исключений из
  контроллера;
- UserRepository ⟶ PostgreSQL по JDBC/JPA;
- RefreshTokenService ⟶ Redis по TCP (через `RedisTemplate`).

### 2.X.7.5. Обоснование структуры

Каждый компонент имеет **одну ответственность** (принцип SRP): контроллер
отвечает за HTTP, AuthService — за бизнес‑логику, JwtService — за работу с
JWT, RefreshTokenService — за Redis. Такое разбиение упрощает
модульное тестирование (каждый компонент изолирован моками) и снижает
порог входа для нового разработчика.

> **ВСТАВИТЬ РИСУНОК.** Файл `07-component.puml`.  
> *Подпись:* «Рисунок — Диаграмма компонентов микросервиса auth-service».

## 2.X.8. Диаграмма развёртывания

**Файл:** `auth-service/docs/uml/plantuml/08-deployment.puml`.

### 2.X.8.1. Назначение

Диаграмма развёртывания (deployment diagram) показывает **физическое
размещение** артефактов на узлах вычислительной инфраструктуры:
устройствах, виртуальных машинах и Docker‑контейнерах.

### 2.X.8.2. Узлы

**`<<device>> Клиент`** — пользовательское устройство (смартфон или
браузер). Содержит артефакт **Mobile/Web App**.

**`<<device>> Docker Host`** — сервер, на котором поднят Docker
Engine. Внутри размещены три вложенных узла:

1. **`<<container>> auth-service` (порт 8080)** — Docker‑контейнер,
   собранный из образа `auth-service:v1`. Содержит артефакт
   **`auth-service.jar`** — упакованное приложение Spring Boot 3.2 на
   Java 17.
2. **`<<device>> PostgreSQL` (порт 5432)** — отдельный контейнер
   с базой `allergen_pg` и таблицей `users`.
3. **`<<device>> Redis` (порт 6379)** — отдельный контейнер для
   хранения refresh‑токенов.

### 2.X.8.3. Соединения

- **Mobile/Web App → auth-service.jar : HTTPS `/auth/*`** — публичный
  канал (проходит через шлюз, на диаграмме показан напрямую для
  упрощения).
- **auth-service.jar → allergen_pg : JDBC** — соединение через
  `spring.datasource.url`. Параметры передаются через переменные
  окружения `SPRING_DATASOURCE_*`.
- **auth-service.jar → refresh tokens : TCP** — соединение через
  `spring.data.redis.host = redis`. Сетевое имя `redis` разрешается
  внутри Docker‑сети.

### 2.X.8.4. Параметры среды развёртывания

В заметке (UML note) к узлу контейнера приложения указаны:

- **Docker image:** `n1vvas1e/auth-service:v1`;
- **Network:** `backend-net` (общая Docker‑сеть для всех контейнеров
  программного комплекса; обеспечивает разрешение имён `postgres`,
  `redis`, `auth-service`, `gateway-service`);
- **Переменные окружения:** `JWT_SECRET` (обязательная — для подписи
  токенов), `SPRING_DATASOURCE_URL`/`USERNAME`/`PASSWORD`,
  `SPRING_DATA_REDIS_HOST`. Все секретные значения изолируются от
  кода и поставляются через `.env`‑файл оркестратора.

### 2.X.8.5. Обоснование выбора Docker и контейнеризации

Контейнеризация выбрана исходя из следующих требований дипломной работы:

- **Воспроизводимость**: одна команда `docker compose up` поднимает весь
  программный комплекс одинаково на машине разработчика и на тестовом
  стенде.
- **Изоляция БД и приложения**: процесс приложения не имеет доступа к
  диску хоста, кроме явно проброшенных томов; конфигурация передаётся
  через переменные окружения.
- **Масштабируемость в перспективе**: каждый контейнер может быть
  отдельно реплицирован, что подготавливает почву для развёртывания
  в Kubernetes без переписывания кода.

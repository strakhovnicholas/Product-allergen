## 2.5.5. Логическая модель данных analytics-service

**analytics-service** отвечает за агрегацию медицинских данных за выбранный период, их аналитическое обогащение (базовые правила и GigaChat), сохранение снимка отчёта и формирование PDF-документа для пользователя. Сервис **не владеет** первичным дневником: записи о питании, симптомах и профиле хранятся в **user-service** и запрашиваются по REST через **gateway-service** (OpenFeign, `UserServiceClient`).

В логической модели выделяются **постоянно хранимые** сущности (PostgreSQL), **транзитные агрегаты** (формируются при генерации отчёта) и **внешние структуры** (получаются из user-service и не дублируются в analytics-service на постоянной основе).

### Постоянное хранение (PostgreSQL, `report_pg`)

#### ReportSnapshot

**Снимок сформированного отчёта** — основная сущность персистентного слоя analytics-service (таблица `report_snapshots`, JPA-сущность `ReportSnapshot`).

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `id` | Long | Идентификатор снимка (PK, автоинкремент) |
| `user_id` | UUID | Идентификатор пользователя (логическая связь с `users.id` auth-service) |
| `period_from` | LocalDateTime | Начало отчётного периода |
| `period_to` | LocalDateTime | Конец отчётного периода |
| `created_at` | LocalDateTime | Момент сохранения снимка |
| `report_data` | JSONB (`ReportData`) | Полный агрегат данных отчёта, включая результат AI-анализа |

Снимок создаётся при каждом успешном вызове `GET /reports/generate`. PDF-файл **в базу не записывается**: документ генерируется по требованию из `report_data` шаблоном JasperReports (`medical_report.jrxml`). Повторная выгрузка PDF выполняется через `GET /reports/snapshots/{id}/pdf`.

> **Примечание.** Сущность `MedicalReport` (таблица `medical_reports`, поле `pdf_content` типа BYTEA) сохранена в кодовой базе как устаревший вариант проектирования и **в рабочем сценарии не используется**. Актуальная модель хранения — `ReportSnapshot` + JSONB.

---

### Транзитный агрегат ReportData

**ReportData** (`ReportDataDto`) — центральная логическая структура отчёта. Формируется в методе `ReportService.collectReportData()`, обогащается AI-слоем, сохраняется в поле `report_data` снимка и передаётся в JasperReports/Kafka.

| Атрибут | Тип | Источник | Назначение |
|---------|-----|----------|------------|
| `user` | UserInfo | `GET /api/user/info` | Медицинский профиль |
| `medicine` | List\<MedicineIntake\> | `GET /api/feelings/medicines?from=&to=` | Журнал приёма лекарств за период (с фильтрацией по `intake_date` на стороне analytics) |
| `wellbeing` | List\<WellbeingEntry\> | `GET /api/feelings/common?from=&to=` | Динамика самочувствия |
| `foodSymptoms` | List\<FoodSymptomLink\> | `GET /api/food-analyzer/analyze?from=&to=` | Связи «пищевой компонент — симптом» |
| `analysis` | AnalysisResult | формируется в analytics-service | Результат аналитической обработки (см. ниже); до обогащения — `null` |

Поле `user_id` на верхнем уровне `ReportData` **отсутствует**: идентификатор пользователя хранится в метаданных `ReportSnapshot` и передаётся в Kafka-сообщениях отдельно.

### Вложенные структуры ReportData (данные из user-service)

Логически они являются **внешними** относительно analytics-service; в снимке отчёта дублируются только в составе JSONB на момент генерации.

### AnalysisResult

**Результат аналитической обработки** (`AnalysisResultDto`). Заполняется в два этапа:

1. **Базовый уровень** — `ReportAnalysisMapper.fromFoodSymptoms()`: из `foodSymptoms` извлекаются списки продуктов и симптомов, по ключевым словам в названиях продуктов выводятся предполагаемые белки-аллергены и микроэлементы.
2. **Обогащение GigaChat** — `GigaChatAnalysisService.enrichReport()`: в модель передаётся сериализованный `ReportData`; ответ LLM парсится в JSON и дополняет или заменяет поля базового уровня.

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `symptoms` | List\<String\> | Симптомы, значимые для периода |
| `products` | List\<String\> | Продукты/компоненты, потенциально связанные с симптомами |
| `dangerous_proteins` | List\<String\> | Белки-аллергены, выявленные анализом |
| `trace_elements` | List\<String\> | Микроэлементы/добавки, требующие внимания |
| `doctor_recommendations` | String | Текстовые рекомендации для врача (HTML-фрагмент для PDF) |

В ранней версии проектирования использовались обобщённые поля `detected_correlations`, `risk_factors`, `recommendations`. В текущей реализации они **детализированы** перечисленными атрибутами, что соответствует шаблону JasperReports и контракту ответа GigaChat.

### Сообщение асинхронного контура ReportAiKafkaMessage

При включённом Kafka-контуре (`report.kafka.request-topic` = `report-ai-requests`) в очередь публикуется сообщение:

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `request_id` | UUID | Идентификатор запроса AI-обогащения |
| `user_id` | UUID | Пользователь |
| `period_from` | LocalDateTime | Начало периода |
| `period_to` | LocalDateTime | Конец периода |
| `report_data` | ReportData | Агрегат до обогащения (`analysis` = null) |

Consumer вызывает GigaChat, записывает результат в `report_data.analysis` и сигнализирует оркестратору через `ReportAiRegistry`. При таймауте (по умолчанию 90 с) или ошибке выполняется **прямой** вызов GigaChat без очереди.

### Связи между сущностями

```
User (auth) ──1..*──> ReportSnapshot
                           │
                           └── report_data : ReportData
                                    ├── user : UserInfo          [внешний, копия в JSONB]
                                    ├── medicine[]                 [внешний]
                                    ├── wellbeing[]                [внешний]
                                    ├── foodSymptoms[]             [внешний]
                                    └── analysis : AnalysisResult  [локальный]

ReportData ──(Kafka)──> ReportAiKafkaMessage ──> GigaChat ──> analysis
ReportData ──(Jasper)──> PDF (транзитный byte[], не персистируется)
```

---

### Принцип хранения данных

Поскольку основная масса медицинских записей размещена в **user-service** (MongoDB + PostgreSQL), **analytics-service** не поддерживает полную реплику дневника. При генерации отчёта выполняется **сборка агрегата ReportData** за интервал `[period_from, period_to]`, после обогащения агрегат **фиксируется** в `ReportSnapshot.report_data` (JSONB). Такой подход обеспечивает:

- воспроизводимость отчёта на дату формирования (снимок не меняется при последующих правках дневника);
- повторную генерацию PDF без повторных вызовов user-service и GigaChat;
- соответствие принципу *Database per Service*: analytics владеет только метаданными снимков и сериализованным результатом анализа.

### Сопоставление с устаревшей логической моделью

| Было (ранняя версия) | Стало (текущая реализация) |
|----------------------|---------------------------|
| `ReportData`: `user_id`, `user_info`, `food_history`, `symptoms_history`, `medicines_history`, `wellbeing_history` | `ReportData`: `user`, `medicine`, `wellbeing`, `foodSymptoms`, `analysis` |
| `AnalysisResult`: `detected_correlations`, `risk_factors`, `recommendations` | `AnalysisResult`: `symptoms`, `products`, `dangerous_proteins`, `trace_elements`, `doctor_recommendations` |
| `MedicalReport`: `report_id`, `user_id`, `generated_at`, `report_content` (PDF в БД) | `ReportSnapshot` + JSONB; PDF генерируется по запросу |
| Отдельные истории пищи и симптомов | Агрегированные связи `foodSymptoms` из `/api/food-analyzer/analyze` |

## 2.1. Общая характеристика программного комплекса

### 2.1.1. Назначение и границы системы

Программный комплекс предназначен для сопровождения пользователей с пищевой аллергией и непереносимостью: ведение персонального медицинского профиля, дневника питания и симптомов, выявление возможных пищевых триггеров, формирование отчётов для врача, а также экспресс-проверки безопасности продуктов по штрихкоду или составу с упаковки.

Система реализована в архитектурном стиле **микросервисов**: каждый сервис отвечает за ограниченную предметную область, развёртывается в отдельном контейнере и взаимодействует с другими по HTTP. Единственная точка входа для клиентских приложений — **API Gateway**. Такое разделение обеспечивает:

- независимое масштабирование нагруженных компонентов (шлюз, user-service);
- изоляцию критичного контура аутентификации (auth-service);
- возможность поэтапного ввода новых функций (analytics-service, scan-service) без остановки всего комплекса.

**Технологический стек (общий):** Java 17, Spring Boot 3.x/4.x, Spring Cloud Gateway, PostgreSQL, Redis, MongoDB, OpenFeign, JasperReports, Docker, JWT.

### 2.1.3. Логическая архитектура программного комплекса

Логическая архитектура описывает **уровни** системы (клиент, периметр API, бизнес-сервисы, данные) и **направления** взаимодействия без привязки к конкретным IP-адресам и версиям ОС. Клиент обращается только к **gateway-service**. Шлюз маршрутизирует запросы:

- `/auth/**` → auth-service (без JWT);
- `/api/**` → user-service (JWT + заголовки `X-User-Id`, `X-Internal-Gateway-Token`);
- `/reports/**` → analytics-service;
- `/scan/**` → scan-service.

**analytics-service** для сбора данных обращается к user-service **через тот же gateway** (OpenFeign → `http://gateway-service:8080`), имитируя клиентский контур с доверенными заголовками.

На уровне данных каждый микросервис владеет собственными хранилищами (принцип *Database per Service*): `allergen_pg`, `user_pg` + `health_tracker`, `report_pg`, Redis, Kafka, внешние API (GigaChat, Open Food Facts).

## 2.2. Проектирование API Gateway (gateway-service)

### 2.2.1. Назначение и ответственность

**gateway-service** выполняет роль **reverse proxy** и **периметра безопасности**. В его обязанности входят: маршрутизация HTTP-запросов к целевым микросервисам; проверка access JWT для защищённых путей; добавление в запрос идентификатора пользователя и внутреннего секрета; настройка CORS для браузерных клиентов. Бизнес-логика учёта аллергий в шлюзе **не реализуется** — это принципиальное ограничение, сохраняющее сервис лёгким и устойчивым к изменениям предметной области.

Конфигурация маршрутов (фрагмент `application.yml`):

- `auth_route`: `Path=/auth/**` → `http://auth-service:8080`;
- `user_route`: `Path=/api/**` → `http://user-service:8080`, фильтр `AuthenticationFilter`.

### 2.2.2. Документирование прецедентов (gateway-service)

**UC-GW-01. Проксирование запросов аутентификации** — прецедент используется актором «Клиент» при регистрации, входе, выходе и обновлении токенов. Клиент обращается к единому адресу шлюза по префиксу `/auth/**`. Система перенаправляет HTTP-запрос в **auth-service** без проверки JWT, поскольку на этапе первичной аутентификации access-токен ещё не выдан или недействителен.

**UC-GW-02. Проксирование защищённых API** — прецедент используется при работе с дневником здоровья, профилем пользователя и иными ресурсами под префиксом `/api/**`. Перед передачей запроса в **user-service** (или иной downstream-сервис) обязательно выполняется сценарий проверки JWT и формирования доверенных заголовков.

**UC-GW-03. Проверка JWT (access)** — вложенный прецедент, активируемый в рамках UC-GW-02. Из заголовка `Authorization: Bearer …` извлекается токен; класс `JwtUtils` проверяет подпись (HMAC), срок действия и claim `type=access`. При любой ошибке клиенту возвращается HTTP 401 Unauthorized.

**UC-GW-04. Добавление доверенных заголовков** — вложенный прецедент после успешной проверки JWT. Шлюз модифицирует запрос: добавляет `X-User-Id` (UUID из claim `id`) и `X-Internal-Gateway-Token` (значение `INTERNAL_SECRET`). Downstream-сервисы используют эти заголовки вместо повторного разбора JWT.

**UC-GW-05. Настройка CORS** — прецедент используется браузерным клиентом при кросс-доменных запросах. Глобальная конфигурация `globalcors` разрешает методы GET, POST, PUT, DELETE, OPTIONS, заголовки и credentials. Для нативных мобильных приложений CORS не является обязательным, однако единая конфигурация упрощает разработку веб-версии.

#### Документирование отношений (gateway-service)

| Базовый прецедент | Связанный | Тип | Обоснование |
|-------------------|-----------|-----|-------------|
| UC-GW-02 | UC-GW-03 | **include** | Без валидации токена передача в user-service недопустима |
| UC-GW-02 | UC-GW-04 | **include** | Идентификация пользователя обязательна для каждого защищённого вызова |
| UC-GW-01 | UC-GW-03 | — | Публичные маршруты `/auth/**` не включают проверку access |
| UC-GW-05 | UC-GW-02 | **extend** | CORS — дополнительная возможность для браузера, не для всех клиентов |

## 2.3. Проектирование сервиса аутентификации (auth-service)

### 2.3.1. Назначение и ответственность

**auth-service** обеспечивает **регистрацию**, **аутентификацию** и **управление сессией** на основе пары токенов JWT (access + refresh). Access-токен короткоживущий (по умолчанию 15 минут) и содержит идентификатор пользователя; refresh-токен долгоживущий (7 суток) и хранится в **Redis** с возможностью отзыва. Пароли в PostgreSQL сохраняются в виде хэша (BCrypt через `PasswordEncoder`).

Публичные эндпоинты (все под `/auth`):

| UC | Метод | Описание |
|----|--------|----------|
| UC-A-01 | POST `/auth/register` | Регистрация |
| UC-A-02 | POST `/auth/login` | Вход |
| UC-A-03 | POST `/auth/logout` | Выход, отзыв refresh |
| UC-A-04 | POST `/auth/refresh` | Обновление access по refresh |

### 2.3.2. Документирование прецедентов (auth-service)

**Регистрация (UC-A-01)** — прецедент используется актором «Клиент» при первом обращении к системе. Пользователь передаёт email и пароль. Система выполняет валидацию DTO (`RegisterRequest`), проверяет уникальность email в таблице `users`, хэширует пароль, сохраняет запись в PostgreSQL, генерирует access и refresh токены, сохраняет refresh в Redis с TTL. В ответ возвращается `AuthResponse`.

**Вход в систему (UC-A-02)** — прецедент используется для получения токенов по учётным данным. `AuthenticationManager` проверяет email и пароль; при успехе отзываются прежние refresh-токены пользователя, выдаётся новая пара. При неверных данных — HTTP 401.

**Выход (UC-A-03)** — прецедент завершает сессию: переданный refresh удаляется из Redis (`RefreshTokenService.revokeToken`).

**Обновление токенов (UC-A-04)** — прецедент применяется при истечении access. Система валидирует JWT refresh, проверяет его наличие в Redis, загружает пользователя и выдаёт новый access (refresh может оставаться прежним в зависимости от реализации).

**Валидация входных данных** — общий include-прецедент (Bean Validation на всех DTO).

**Выдача JWT** — include-прецедент для UC-A-01, UC-A-02, UC-A-04 (`JwtService`).

**Хранение refresh в Redis** — include для операций, затрагивающих сессию.

#### Документирование отношений (auth-service)

Все основные UC **include** «Валидацию» и, где применимо, «Выдачу JWT» и «Хранение refresh в Redis». Связи отражены на диаграмме вариантов использования (рис. 2.10).

| Поле | Тип | Назначение |

## 2.4. Проектирование пользовательского сервиса (user-service)

### 2.4.1. Назначение и ответственность

**user-service** — **ядро предметной области** комплекса. В нём реализованы: медицинский профиль пользователя; дневник приёмов пищи; учёт симптомов и самочувствия; справочники продуктов и лекарств; заметки; **анализатор корреляции «компонент питания — симптом»** за выбранный период.

Сервис не выполняет аутентификацию по паролю: он **доверяет** gateway, проверяя `X-Internal-Gateway-Token` (`InternalGatewayFilter`) и извлекая `X-User-Id` (`UserIdArgumentResolver`, аннотация `@CurrentUserId`).

### 2.4.2. Документирование прецедентов (user-service)

**UC-U-01. Управление профилем** — прецедент используется актором «Пользователь» для создания и ведения данных: ФИО, возраст, вес, рост, пол, курение, алкоголь, спорт, хронические заболевания, **список аллергенов**, предрасположенность, регулярные препараты. API: `POST/GET/PUT/DELETE /api/user/info`. Данные хранятся в MongoDB, коллекция `user_info`.

**UC-U-02. Учёт приёмов пищи** — прецедент используется для фиксации съеденных продуктов: наименование, категория, количество, единица измерения, время приёма, **список компонентов** (ингредиентов) для последующего анализа. API: `/api/feelings/food`. Коллекция MongoDB `food_intakes`.

**UC-U-03. Учёт симптомов** — прецедент используется для записи аллергических и иных реакций с привязкой ко времени. API: `/api/feelings/symptoms`. Коллекция `symptoms`.

**UC-U-04. Учёт самочувствия** — прецедент используется для ежедневной оценки состояния по шкале. API: `/api/feelings/common`. Коллекция `common_feelings`.

**UC-U-05. Учёт лекарств** — прецедент включает ведение справочника препаратов (`/api/medicines`, PostgreSQL) и фиксацию фактов приёма (`/api/feelings/medicines`).

**UC-U-06. Заметки** — произвольные текстовые записи дневника (`/api/notes`, MongoDB `notes`).

**UC-U-07. Анализ «еда — симптом»** — прецедент используется пользователем или **analytics-service** при наличии данных за период `[from, to]`. `FoodAnalyzerServiceFacade` загружает приёмы пищи и симптомы, `FoodComponentAnalyzerServiceImpl` для каждого компонента питания определяет симптомы в окне `symptomAppearanceTimeHours` (из `app-config.properties`) и формирует список `FoodComponentSymptomsResponse`. API: `GET /api/food-analyzer/analyze`.

**UC-U-08. Справочник продуктов** — CRUD пользовательского каталога (`/api/food`, JPA `FoodEntity`).

**UC-U-09. Справочник симптомов** — управление перечнем возможных симптомов (`/api/symptoms`, `SymptomEntity`).

**Проверка внутреннего токена шлюза** — include для всех UC-U-01…09.

**Извлечение X-User-Id** — include; исключает подмену userId в теле запроса.

#### Документирование отношений (user-service)

- UC-U-07 **extend** UC-U-02 и UC-U-03: анализ возможен только при накопленных записях о питании и симптомах.
- Все UC **include** проверку токена шлюза и извлечение идентификатора пользователя.

### 2.4.3. Проектирование хранения данных user-service

Применена **гибридная модель**:

**PostgreSQL (`user_pg`)** — структурированные справочники и связи JPA:

- `FoodEntity` — каталог продуктов;
- `MedicineEntity`, `IntakeMedicineEntity` — лекарства и приёмы;
- `SymptomEntity` — справочник типов симптомов.

**MongoDB (`health_tracker`)** — гибкие документы дневника:

- `user_info`, `food_intakes`, `symptoms`, `common_feelings`, `notes`.

**ВСТАВИТЬ РИСУНОК 2.50 и 2.51** — физические модели user-service: `database/05-physical-user-postgresql.puml` и `database/06-physical-user-mongodb.puml`. *(Рис. 2.19 в ранней нумерации заменён на 2.50–2.51.)*

### 2.4.4. Алгоритм анализатора (краткое проектное описание)

Для каждого компонента питания с меткой времени алгоритм:

1. определяет «безопасные» компоненты — после приёма которых в течение N часов не было симптомов;
2. для остальных находит симптомы в интервале `[время приёма; время приёма + N часов]`;
3. возвращает карту «компонент → множество потенциальных симптомов».

Параметр N задаётся конфигурацией `food-analyzer.safe-time-after-food-intake`.

## 2.5. Проектирование сервиса аналитики (analytics-service)

### 2.5.1. Назначение и ответственность

**analytics-service** формирует **медицинский PDF-отчёт** за период для передачи врачу или личного архива. Отчёт включает: данные профиля; список принятых лекарств; динамику самочувствия; результаты пищевого анализатора; текстовое заключение (базовое — из агрегации симптомов; расширенное — через GigaChat по асинхронному каналу Kafka).

Межсервисное взаимодействие: `UserServiceClient` (OpenFeign) → `http://gateway-service:8080` с теми же заголовками, что и клиент.

### 2.5.2. Документирование прецедентов (analytics-service)

**UC-AN-01. Генерация медотчёта** — прецедент используется актором «Клиент» (через gateway). Параметры `from`, `to`. `ReportService.fillReport` запрашивает у user-service профиль, лекарства, самочувствие, результат `/api/food-analyzer/analyze`, формирует `ReportDataDto`, заполняет шаблон JasperReports (`medical_report.jrxml`), возвращает PDF. API: `GET /reports/generate`.

**UC-AN-02. Скачивание PDF** — прецедент генерирует PDF из переданной структуры `ReportDataDto` без повторного сбора данных. API: `GET /reports/download`.

**Проверка X-Internal-Gateway-Token** — include (`InternalGatewayFilter`).

**Загрузка данных через Feign** — include для UC-AN-01.

**Формирование PDF (JasperReports)** — include для UC-AN-01 и UC-AN-02.

**AI-анализ (Kafka → GigaChat)** — extend к UC-AN-01: публикация `ReportDataDto` в топик `report-data-requests`, асинхронный consumer, вызов GigaChat API, обогащение поля `analysis`.

**Сохранение отчёта в PostgreSQL** — extend: сущность `MedicalReport` (userId, createdAt, status, pdf_content bytea).

#### Документирование отношений (analytics-service)

- UC-AN-01 **include** проверку шлюза, Feign, PDF;
- UC-AN-01 **extend** AI-анализ и сохранение в БД (опциональные расширения);
- UC-AN-02 **include** PDF, без Feign.

## 2.6. Проектирование сервиса сканирования продукта (scan-service)

### 2.6.1. Назначение

**scan-service** автоматизирует проверку продукта **до покупки или употребления**: по штрихкоду (EAN/UPC) или по фото состава на этикетке. Результат сопоставляется с аллергенами из профиля user-service.

### 2.6.2. Документирование прецедентов (scan-service)

**Сканирование штрихкода** — прецедент используется актором «Пользователь». Камера передаёт код; система запрашивает состав во внешней БД (Open Food Facts или локальный кэш).

**Распознавание состава с этикетки (OCR)** — прецедент используется, если штрихкод не найден. OCR извлекает ингредиенты и фразы «может содержать следы…».

**Сопоставление с профилем аллергенов** — прецедент активируется после получения состава. Feign-запрос `GET /api/user/info` через gateway; сравнение списков аллергенов, глютена, орехов, E-добавок.

**Оценка риска** — прецедент формирует вердикт: «рекомендуется / с осторожностью / не рекомендуется» с расшифровкой.

**Добавление в дневник питания** — прецедент **extend**: по запросу пользователя вызывается `POST /api/feelings/food` в user-service.

#### Отношения (scan-service)

| Связь | Тип | Обоснование |
|-------|-----|-------------|
| Сканирование → Сопоставление | include | Без состава оценка невозможна |
| OCR → Сканирование | extend | Альтернативный вход |
| Оценка риска → Сопоставление | include | |
| Добавление в дневник → Оценка риска | extend | Опционально |

# 4.5. Выводы по тестированию (актуальная редакция)

В рамках данной главы была выполнена комплексная проверка корректности работы программного комплекса **Product-allergen**, включающего пять backend-микросервисов (**gateway-service**, **auth-service**, **user-service**, **analytics-service**, **scan-service**) и клиентское приложение на **React Native (Expo)**. Основное внимание уделено модульному и интеграционному тестированию бизнес-логики, сервисного слоя и REST API, что обеспечило изоляцию компонентов и детерминированность результатов там, где это возможно без обращения к внешним недетерминированным API.

Для реализации тестирования применялись средства экосистемы **Spring Boot** и **JUnit 5**: **Mockito** и **AssertJ** — для изолированных юнит-тестов (**auth-service**), **MockMvc** и **`@WebMvcTest`** — для проверки HTTP-контрактов контроллеров (**user-service**, **gateway-service**, **analytics-service**, **scan-service**), а также стандартные тесты DTO, мапперов и доменной логики. Сквозные сценарии «регистрация → дневник → отчёт → сканирование этикетки» дополнительно проверялись вручную на развёрнутом Docker-стенде с **gateway** (порт 8080), **Swagger UI** и мобильным клиентом.

По **auth-service** (19 автоматизированных тестов) подтверждены генерация и валидация JWT access/refresh-токенов, сценарии регистрации и входа, обновление и отзыв refresh-токенов в **Redis**, а также валидация входных DTO. Это закрывает критичный контур безопасности всего комплекса.

По **user-service** (63 теста) проверены алгоритм выявления пищевых триггеров (**FoodComponentAnalyzerServiceImpl**), преобразователи дат и ответов анализатора, а также REST API дневника: заметки, симптомы, приёмы пищи, общее самочувствие, профиль пользователя, справочники блюд, лекарств и симптомов. Отдельно подтверждена работа механизма идентификации пользователя через заголовок **X-User-Id** и обработка запросов без этого заголовка (код **400**).

По **gateway-service** (12 тестов) автоматизирована проверка JWT-фильтра и маршрутизации: отказ **401** без токена, успешная передача **X-User-Id** и **X-Internal-Gateway-Token** при валидном access-токене, корректная работа публичного префикса `/auth/**` без проверки JWT на шлюзе.

По **analytics-service** (20 тестов) проверены маппинг снимков отчётов (**ReportSnapshot**), агрегация симптомов и пищевых триггеров (**ReportAnalysisMapper**), сохранение и получение snapshot-данных, REST API генерации и выгрузки отчётов в **PDF**, а также подъём Spring-контекста в тестовом профиле без реального **GigaChat** и **Kafka**. Негативные сценарии (отсутствие обязательных параметров запроса) покрыты на уровне контроллера.

По **scan-service** (14 тестов) охвачены анализ изображения состава продукта (с изоляцией **ScanService**), in-memory хранение истории сканирований, fallback при не настроенном **GigaChat**, REST API **`POST /scans/analyze`**, **`GET /scans/{id}`**, **`GET /scans/history`**, а также обработка отсутствия файла **image** (код **400**). Поведение vision-модели в продуктиве дополнительно верифицируется ручными прогонами и логами с префиксом **[ScanAI]**.

**Клиентское приложение** (Expo) на этапе диплома проверялось по чек-листу из восьми сценарных тестов (регистрация, дневник, отчёт, сканер, выход из системы и др.); отдельный пакет Jest/Vitest не выделялся, что соответствует ограничениям прототипа.

**Сводка автоматизированного backend-тестирования:** порядка **128** тестов в **20+** тестовых классах; при прогоне `mvn test` в каждом модуле все сценарии завершились успешно. Критических дефектов в логике аутентификации, дневника, шлюза, отчётов и сканирования не выявлено.

Полученные результаты свидетельствуют о стабильности выбранной микросервисной архитектуры, корректной изоляции компонентов при тестировании и высокой степени покрытия ключевых сценариев автоматизированными проверками. Для промышленной эксплуатации целесообразно развитие CI/CD с единым прогоном тестов всех модулей и, при необходимости, добавление Testcontainers для полного интеграционного контура с **PostgreSQL**, **MongoDB** и **Kafka**.

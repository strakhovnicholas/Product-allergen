## 2.6.5. Физическая модель analytics-service

Сервис аналитики **analytics-service** использует реляционную СУБД **PostgreSQL** (база `report_pg`, порт 5433 в Docker-развёртывании) для хранения **снимков сформированных отчётов**. MongoDB в analytics-service **не применяется**.

Основная таблица — **report_snapshots**:

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | BIGSERIAL | Первичный ключ снимка |
| `user_id` | UUID | Идентификатор пользователя (из auth-service) |
| `period_from` | TIMESTAMP | Начало отчётного периода |
| `period_to` | TIMESTAMP | Конец отчётного периода |
| `created_at` | TIMESTAMP | Момент сохранения снимка |
| `report_data` | JSONB | Агрегированные данные отчёта и результат анализа |

Поле **report_data** сериализует объект `ReportDataDto`: медицинский профиль, приёмы лекарств, самочувствие, связи «пищевой компонент — симптом» (полученные из user-service на момент генерации) и блок **analysis** с результатами аналитической обработки.

Пример фрагмента JSONB (`report_data`):

```json
{
  "user": {
    "fullName": "Иванов И.И.",
    "allergies": ["молоко", "орехи"],
    "chronicDiseases": ["астма"]
  },
  "medicine": [
    {
      "name": "Цетиризин",
      "dosage": "10",
      "unit": "мг",
      "intakeDate": "2025-01-15T08:00:00"
    }
  ],
  "wellbeing": [
    { "dateTime": "2025-01-15T20:00:00", "score": 6 }
  ],
  "foodSymptoms": [
    {
      "foodComponentName": "лактоза",
      "symptomsName": ["боль в животе", "вздутие"]
    }
  ],
  "analysis": {
    "symptoms": ["боль в животе", "вздутие"],
    "products": ["йогурт", "лактоза"],
    "dangerousProteins": ["казеин"],
    "traceElements": [],
    "doctorRecommendations": "<p>Рекомендуется...</p>"
  }
}
```

**PDF-отчёт в базе не сохраняется**: файл формируется по запросу шаблоном JasperReports (`medical_report.jrxml`) из содержимого `report_data` и возвращается клиенту (`GET /reports/generate`, `GET /reports/snapshots/{id}/pdf`).

Отдельных коллекций `reports` и `analysis_results` **нет** — в устаревшем варианте проектирования они ошибочно относились к MongoDB. Результат анализа входит в JSONB-поле `report_data.analysis`.

Устаревшая таблица **medical_reports** (хранение PDF в BYTEA) в рабочем сценарии **не используется**.

Связь с пользователем — поле `user_id` (логическая связь с auth-service, без межсервисного FK). Данные дневника в analytics-service **не дублируются постоянно**: при генерации отчёта выполняется сбор через Feign из user-service, после обогащения GigaChat результат фиксируется в снимке.

Для повышения производительности создан индекс:

- **idx_report_snapshots_user_id** (`user_id`) — список снимков пользователя (`GET /reports/snapshots`).

Дополнительно при выборке по периоду используются поля `period_from`, `period_to`, `created_at` (при необходимости можно добавить составной индекс `{user_id, created_at}`).

Использование типа **JSONB** в PostgreSQL обеспечивает хранение результатов анализа произвольной вложенной структуры (массивы симптомов, продуктов, рекомендаций LLM) в рамках реляционной модели и упрощает расширение аналитических алгоритмов без изменения схемы таблицы при добавлении новых полей в `ReportDataDto`.

## Сопоставление со старым текстом

| Было (устаревшее) | Стало |
|-------------------|-------|
| MongoDB, коллекции `reports`, `analysis_results` | PostgreSQL, таблица `report_snapshots` |
| `pdfUrl` в документе | PDF генерируется on-demand, URL/файл в БД не хранится |
| `riskFactors`, `recommendations` | `analysis`: `dangerousProteins`, `traceElements`, `doctorRecommendations` и др. |
| Индексы `userId`, `generatedAt` | `idx_report_snapshots_user_id`; дата — `created_at` |

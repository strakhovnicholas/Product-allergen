## ВВЕДЕНИЕ

В последние десятилетия аллергические заболевания закрепились в числе наиболее распространённых хронических состояний и оказывают существенное влияние на общественное здоровье, экономику здравоохранения и качество жизни населения. По оценкам Всемирной организации здравоохранения (ВОЗ), аллергические и гиперчувствительные состояния затрагивают сотни миллионов человек во всём мире; в отдельных регионах доля населения с проявлениями аллергического ринита и связанных состояний достигает 20–30 % и выше [1]. Для Российской Федерации характерен устойчивый рост обращений по поводу аллергических реакций и бронхиальной астмы, что подтверждается динамикой статистики первичной заболеваемости и диспансерного наблюдения [2].

Социально-экономические последствия проявляются в снижении трудоспособности, увеличении расходов на лекарственную терапию, росте числа внеплановых обращений к врачу и снижении качества сна и повседневной активности. По данным исследований в области аллергологии, непрерывный и систематический самоконтроль симптомов, триггеров и терапии позволяет сократить частоту обострений и повысить эффективность врачебных решений; однако на практике пациенты фиксируют данные фрагментарно — в бумажных записях, мессенджерах или обезличенных заметках.

Цифровизация персонального здравоохранения (Digital Health) создаёт предпосылки для перехода от эпизодического реагирования на симптомы к **проактивному мониторингу**. Согласно отчётам аналитических агентств, мировой рынок mHealth (мобильного здравоохранения) демонстрирует среднегодовой темп роста порядка 10–14 %; к 2030 году его объём может превысить 300 млрд долл. США [3]. Сегмент приложений для хронических состояний, включая аллергию и пищевую непереносимость, относится к наиболее динамичным направлениям.

**Цель дипломной работы** — разработка программного комплекса Product-allergen: мобильного клиента и серверной микросервисной платформы для ведения цифрового дневника аллергика, анализа взаимосвязей «фактор — симптом», формирования медицинских отчётов и экспресс-проверки состава продуктов по фотографии этикетки с учётом индивидуального профиля пользователя.

**Объект исследования** — процессы сбора, хранения и анализа медицински значимых данных при самоконтроле аллергических состояний.

**Предмет исследования** — методы и программные средства построения распределённой информационной системы с мобильным клиентом и серверными микросервисами.

**Практическая значимость** заключается в повышении полноты и структурированности данных, передаваемых врачу, снижении риска пропуска приёма препаратов, ускорении выявления потенциально опасных компонентов в продуктах питания и сокращении времени на подготовку аналитики за счёт автоматизации (в том числе с применением больших языковых моделей).

**Структура работы.** Глава 1 посвящена технико-экономическому обоснованию; глава 2 — проектированию; глава 3 — реализации; глава 4 — тестированию и оценке результатов.

## 1 Технико-экономическое обоснование

### 1.1 Обоснование актуальности темы проекта

#### 1.1.1. Описание проблемы

Аллергические заболевания характеризуются **многофакторной природой**: на течение состояния влияют сезонная пыльца, пищевые продукты, бытовые аллергены, лекарственная терапия, метеорологические условия и индивидуальные особенности организма. Пациенту необходимо одновременно:

- фиксировать симптомы и их выраженность во времени;
- учитывать приём лекарственных препаратов;
- отслеживать приёмы пищи и потенциальные пищевые триггеры;
- соблюдать рекомендации лечащего врача;
- своевременно оценивать безопасность продуктов до употребления.

При отсутствии специализированного цифрового инструмента возникают системные проблемы:

1. **Неполнота данных** — записи ведутся нерегулярно, теряется привязка «событие — время — интенсивность».
2. **Субъективность анализа** — пользователь и врач опираются на память пациента, а не на объективную динамику.
3. **Разрозненность информации** — симптомы, питание и терапия хранятся в разных носителях.
4. **Высокая трудоёмкость подготовки к приёму** — врач тратит значительную часть консультации на восстановление истории болезни.
5. **Риски при выборе продуктов** — сложный состав на этикетке затрудняет самостоятельную оценку аллергенности.

С точки зрения информационных технологий проблема формулируется как **отсутствие интегрированной информационной системы**, объединяющей персональный медицинский профиль, дневник наблюдений, аналитику и интеллектуальную обработку данных в едином защищённом контуре.

#### 1.1.2. Обоснование необходимости решения проблемы

Необходимость разработки обусловлена совокупностью медицинских, социальных и технологических факторов.

**Медико-социальные факторы:**

- рост распространённости аллергических состояний в популяции (в т.ч. среди детей — с увеличением доли пищевой аллергии) [1, 2];
- удлинение периода наблюдения за хроническими пациентами и переход к модели долгосрочного амбулаторного сопровождения;
- дефицит времени врача на детальный разбор дневниковых записей.

**Поведенческие факторы:**

- низкая приверженность терапии (пропуски приёма препаратов) — по различным исследованиям затрагивает от 30 до 50 % пациентов с хроническими заболеваниями [4];
- потребность в наглядной обратной связи (графики, отчёты, напоминания).

**Технологические факторы:**

- повсеместное использование смартфонов (в РФ проникновение мобильного интернета превышает 85 % населения [5]);
- зрелость облачных API для обработки естественного языка и компьютерного зрения (в т.ч. GigaChat, что позволяет реализовать анализ этикеток без обучения собственных моделей на этапе дипломного проекта);
- распространение микросервисной архитектуры в healthcare IT, обеспечивающей масштабируемость и изоляцию данных.

**Прогноз:** при сохранении текущих тенденций спрос на персонализированные цифровые сервисы самоконтроля хронических состояний будет расти опережающими темпами по сравнению с классическими информационными системами медицинских организаций, ориентированными на врача, а не на пациента.

#### 1.1.3. Технический и экономический эффект от решения проблемы

**Технический эффект** для пользователя и системы здравоохранения:

| Показатель | До внедрения | После внедрения (ожидаемый эффект) |
|------------|--------------|-------------------------------------|
| Полнота фиксации симптомов | Эпизодическая, ~30–40 % дней | Регулярная, целевой показатель ≥70 % дней |
| Время подготовки данных к приёму врача | 40–90 мин (ручной сбор) | 5–15 мин (автоотчёт PDF) |
| Время оценки состава продукта | 3–10 мин (чтение этикетки) | 10–30 с (фото + автоматический разбор) |
| Выявление корреляций «еда — симптом» | Субъективно, редко | Автоматизированный анализ за период |
| Доступность истории | Разрозненные записи | Единое хранилище с резервированием |

**Экономический эффект** (оценочный, для сегмента пользователей приложения):

Рассмотрим упрощённую модель для **одного активного пользователя** в год:

- экономия времени на подготовке к врачу: 6 консультаций × 1 ч = 6 ч; при стоимости часа времени пользователя 500 руб. → **3 000 руб./год**;
- снижение риска покупки неподходящих продуктов и повторных обострений: условная оценка **2 000–5 000 руб./год** (меньше внеплановых покупок лекарств и специализированных продуктов);
- повышение приверженности терапии: потенциальное снижение числа обострений на 10–15 % (по аналогии с mHealth-интервенциями для хронических заболеваний) [4].

Для **1000 пользователей** совокупный общественный эффект может составить **5–8 млн руб. в год** (оценка порядка величины, подлежит уточнению пилотным исследованием).

Для **разработчика/оператора** системы экономический эффект проявляется в:

- возможности монетизации подписки (базовый дневник — бесплатно, расширенная аналитика и отчёты — платно);
- снижении стоимости сопровождения за счёт типовой микросервисной архитектуры (масштабирование отдельных сервисов: аналитика, сканер);
- использовании готовых облачных API ИИ на этапе MVP вместо капитальных затрат на обучение моделей (экономия **1,5–3 млн руб.** на этапе запуска по сравнению с собственной ML-платформой).

**Технический эффект для ИТ-инфраструктуры:** микросервисная архитектура (auth, user, analytics, scan, gateway) обеспечивает независимое масштабирование нагруженных компонентов (отчёты, GigaChat, сканирование) и отказоустойчивость: сбой одного сервиса не останавливает весь комплекс.

#### 1.1.4. Существующие решения и их недостатки

На российском и международном рынке представлены приложения смежной направленности. Наиболее близкие по части функций — **Pollen Club** (мониторинг пыльцы и базовый дневник) и **IQAir AirVisual** (качество воздуха и прогноз пыльцы). Специализированных комплексных решений для ведения дневника аллергика с учётом питания, терапии, отчётности для врача и анализа этикеток по фото — **незначительное количество**.

**Недостатки Pollen Club:**

- узкая направленность (пыльца, крупные города);
- отсутствие полноценного учёта лекарств и пищевых триггеров;
- слабая аналитика динамики симптомов;
- устаревший UX, навязчивая реклама (по отзывам пользователей).

**Недостатки IQAir AirVisual:**

- информационный характер без персонального дневника;
- нет учёта терапии и формирования медицинских отчётов;
- нет персонализации под профиль аллергий пользователя.

**Общий недостаток рынка:** отсутствие связки «дневник + ИИ-аналитика + сканирование состава + микросервисный backend» в одном продукте.

#### 1.1.6. Вывод о необходимости нового решения и его преимущества

Проведённый анализ показывает, что существующие решения **не закрывают комплекс потребностей** пациента-аллергика в единой системе. Необходима разработка нового программного комплекса Product-allergen.

**Преимущества разрабатываемого решения:**

1. **Комплексность** — дневник, терапия, аналитика, отчёты и сканер в одной экосистеме.
2. **Персонализация** — учёт индивидуального профиля аллергенов и предрасположенности.
3. **Поддержка врача** — структурированный PDF-отчёт вместо «сырых» записей.
4. **ИИ как ассистент, а не замена врача** — GigaChat для сводок и разбора этикеток; решения по лечению остаются за специалистом.
5. **Масштабируемая архитектура** — микросервисы, отдельные БД, API Gateway.
6. **Практическая реализуемость** — использование зрелого стека (Java, Spring Boot, Expo, PostgreSQL, MongoDB).
7. **Расширяемость** — возможность добавления iOS/Web-клиентов без изменения контрактов API.

**Роль ИИ-модуля.** Система не ставит диагноз и не назначает лечение. ИИ формирует: корреляции, динамику, краткую сводку для врача, рекомендации общего характера («обратитесь к врачу при ухудшении»). Это снижает регуляторные риски и соответствует позиции вспомогательного ПО.

**Перспектива коммерциализации:** замена облачного API на собственную модель при росте пользовательской базы; внедрение подписной модели; интеграция с клиниками.

### 1.2 Обоснование выбора программных средств

*(Пункт 7 структуры ТЭО — с обоснованием преимуществ перед аналогами)*

#### 1.2.1. Архитектурный подход

Выбрана **микросервисная архитектура** с API Gateway (единая точка входа, JWT, маршрутизация). Альтернатива — монолит — проще на старте, но хуже масштабируется при росте нагрузки на аналитику и сканирование. Микросервисы соответствуют предметной области (изолированные контуры: учётные записи, дневник, отчёты, сканер).

#### 1.2.2. Серверная часть: Java и Spring Boot

| Критерий | Java + Spring Boot | Node.js (Express) | Python (Django/FastAPI) |
|----------|-------------------|-------------------|-------------------------|
| Типизация | Статическая | Динамическая | Динамическая |
| Экосистема enterprise | Обширная | Хорошая | Хорошая для ML |
| Spring Security, JPA | Встроено | Требует сборки | Аналоги есть |
| Распространённость в РФ | Высокая | Высокая | Высокая |

**Вывод:** Java 17 и Spring Boot 3.x — для надёжного REST API, безопасности (JWT), интеграции с PostgreSQL/MongoDB/Redis/Kafka.

#### 1.2.3. Клиентское приложение: Expo (React Native)

В дипломном проекте клиент реализован на **Expo (React Native, TypeScript)**, а не на отдельном нативном Android (Kotlin).

| Критерий | Expo / React Native | Нативный Android (Kotlin) | Flutter |
|----------|---------------------|---------------------------|---------|
| Кроссплатформенность | Android, iOS, Web | Только Android | Android, iOS, Web |
| Скорость разработки | Высокая | Средняя | Высокая |
| Доступ к камере | expo-camera | Нативный API | camera plugin |
| Единый код с дипломом | Да (репозиторий) | Потребует переписывания | Потребует переписывания |

**Вывод:** Expo выбран как средство быстрой разработки MVP с перспективой iOS; серверный REST API остаётся платформо-независимым.

#### 1.2.4. Системы управления данными

| Назначение | СУБД | Альтернатива | Почему выбрано |
|------------|-----|--------------|----------------|
| Учётные записи, отчёты | PostgreSQL | MySQL | ACID, Spring Data JPA, JSON при необходимости |
| Дневник (гибкая схема) | MongoDB | PostgreSQL JSON | Гибкость документов без частых миграций |
| Refresh-токены | Redis | PostgreSQL | TTL, скорость, типовой паттерн для JWT |
| Асинхронная аналитика | Apache Kafka | RabbitMQ | Потоковая обработка отчётов, масштабирование consumer |

## 3.1. Общая характеристика этапа разработки

На этапе разработки программный комплекс Product-allergen был реализован в виде пяти микросервисов, спроектированных в главе 2. Каждый сервис — отдельный Maven-модуль на **Java 17** и **Spring Boot 3.x**, упакованный в Docker-образ и развёрнутый в сети `backend-net`.

Результатом разработки является **работающая программа**: REST API через единый шлюз, хранение в PostgreSQL, MongoDB, Redis, Kafka, интеграция с **GigaChat** (отчёты и анализ этикеток в scan-service).

### 3.1.1. Структура исходного кода

| Микросервис | Репозиторий | Пакет / каталог исходников |
|-------------|-------------|----------------------------|
| gateway-service | Product-allergen-gateway | `gateway/src/main/java/ru/productallergen/gateway/` |
| auth-service | Product-allergen-auth | `auth-service/src/main/java/ru/productallergen/authservice/` |
| user-service | Product-allergen-user | `user-service/src/main/java/ru/productallergen/userservice/` |
| analytics-service | Product-allergen-new | `analytics-service/src/main/java/ru/productallergen/analytics/` |
| scan-service | Product-allergen-new (модуль scan) | `scan-service/src/main/java/` *(по структуре UML)* |

UML-диаграммы реализации (варианты использования, последовательности, классов, компонентов, развёртывания) для каждого сервиса приведены в подразделах 3.2–3.6. Нумерация рисунков главы 3 продолжает логику главы 2: **рисунки 3.1–3.40** — по восемь диаграмм на каждый из пяти сервисов.

### 3.1.2. Сквозной технологический стек реализации

- **Spring Web / Spring Cloud Gateway** — HTTP-слой;
- **Spring Data JPA** — PostgreSQL (auth, user, analytics, scan);
- **Spring Data MongoDB** — дневник user-service;
- **Spring Data Redis** — refresh-токены auth-service;
- **Spring Security** — аутентификация в auth-service;
- **OpenFeign** — межсервисные вызовы analytics → gateway → user;
- **JasperReports** — генерация PDF в analytics-service;
- **Spring Kafka** — асинхронная передача `ReportDataDto` для AI-обогащения;
- **Docker Compose** — локальное и продуктивное развёртывание.

## 3.2. Разработка API Gateway (gateway-service)

### 3.2.1. Назначение реализованного модуля

**gateway-service** — единственная внешняя точка входа (порт **8080**). Реализован на **Spring Cloud Gateway** (реактивный стек). Модуль не содержит бизнес-логики аллергий: он маршрутизирует запросы, проверяет JWT для защищённых маршрутов и добавляет доверенные заголовки для downstream-сервисов.

Конфигурация маршрутов (`gateway/src/main/resources/application.yml`):

- `Path=/auth/**` → `http://auth-service:8080` (без фильтра JWT);
- `Path=/api/**` → `http://user-service:8080` с фильтром `AuthenticationFilter`.

### 3.2.2. Основные классы

| Класс | Назначение |
|-------|------------|
| `GatewayApplication` | Точка входа Spring Boot |
| `AuthenticationFilter` | Фабрика фильтра Gateway: извлечение Bearer-токена, валидация, заголовки `X-User-Id`, `X-Internal-Gateway-Token` |
| `JwtUtils` | Проверка подписи и срока JWT, извлечение claim `id` |
| `Config` (вложенный класс фильтра) | Флаг `skipAuth` для тестового режима |

Класс `AuthenticationFilter` при успешной проверке модифицирует запрос:

```java
ServerHttpRequest modifiedRequest = request.mutate()
    .header(X_USER_ID, userId)
    .header(X_INTERNAL_TOKEN, internalSecret)
    .build();
```

При отсутствии или невалидности токена возвращается **HTTP 401** без обращения к user-service — это снижает нагрузку и исключает обход периметра.

#### Реализация прецедентов шлюза (по диаграммам)

**UC-GW-01 — проксирование `/auth/**` (рис. 3.3).** Запросы регистрации и входа не содержат access-токена. Gateway перенаправляет HTTP-поток в auth-service без вызова `AuthenticationFilter`, сохраняя тело JSON и коды ответов 200/401/409.

**UC-GW-02 — защищённый API (рис. 3.2).** Для `/api/**` цепочка реактивного фильтра выполняется до `NettyRoutingFilter`. Ошибка на любом шаге завершает exchange с 401 — user-service не вызывается.

**UC-GW-03 — отказ в доступе (рис. 3.4).** Сценарий документирует поведение при просроченном access, подделанной подписи или отсутствии префикса `Bearer `. Клиент должен инициировать refresh или повторный login.

**CORS (рис. 3.5).** Глобальная секция `globalcors` в `application.yml` разрешает методы GET/POST/PUT/DELETE/OPTIONS и заголовок `Authorization`, что необходимо для SPA и мобильных WebView.

**Компоненты (рис. 3.7).** Видны границы: Spring Cloud Gateway, кастомный фильтр, утилита JWT, внешние контейнеры auth и user. Связь «зависимость» означает использование одного `JWT_SECRET` на этапе валидации (секрет задаётся переменной окружения в Docker).

**Развёртывание (рис. 3.8).** Контейнер `gateway-service` публикует порт 8080 наружу; внутренняя сеть `backend-net` скрывает порты микросервисов от интернета.

## 3.3. Разработка сервиса аутентификации (auth-service)

### 3.3.1. Назначение и REST API

**auth-service** реализует регистрацию, вход, выход и обновление пары токенов. Контроллер `AuthController` (`@RequestMapping("/auth")`) предоставляет:

| Метод | Путь | Действие |
|-------|------|----------|
| POST | `/auth/register` | Создание учётной записи, выдача access + refresh |
| POST | `/auth/login` | Проверка пароля, выдача токенов |
| POST | `/auth/logout` | Отзыв refresh-токена в Redis |
| POST | `/auth/refresh` | Новый access по действующему refresh |

Ответ унифицирован DTO `AuthResponse` (accessToken, refreshToken). Валидация входных данных — Jakarta Bean Validation на `LoginRequest`, `RegisterRequest`.

### 3.3.2. Реализация бизнес-логики

Класс **`AuthService`** координирует:

1. **Регистрация** — проверка `userRepository.existsByEmail`, хеширование пароля `PasswordEncoder` (BCrypt), сохранение сущности `User`, генерация JWT, запись refresh в Redis.
2. **Вход** — `AuthenticationManager` + `UsernamePasswordAuthenticationToken`, отзыв старых refresh для email (`revokeOldTokensByEmail`), выдача новой пары.
3. **Refresh** — двойная проверка: подпись JWT (`JwtService.validateToken(..., "refresh")`) и наличие ключа в Redis (`RefreshTokenService.isValid`).
4. **Logout** — удаление ключа refresh и исключение из множества `user_tokens:<email>`.

Класс **`JwtService`** формирует токены на **HS256** с claim `id` (UUID пользователя) и `type` (`access` / `refresh`). Сроки из конфигурации: access — 900000 мс (15 мин), refresh — 604800000 мс (7 сут).

### 3.3.3. Работа с базами данных

**PostgreSQL (`allergen_pg`), таблица `users`**

Сущность `User` (`@Entity`, `@Table(name = "users")`):

- `id` — UUID, `@GeneratedValue(strategy = GenerationType.UUID)`;
- `email` — уникальный, NOT NULL;
- `password` — хеш BCrypt;
- `is_active`, `created_at`, `updated_at` — служебные поля.

Типовые запросы (через Spring Data JPA):

```sql
-- при регистрации
INSERT INTO users (id, email, password, is_active, created_at, updated_at) VALUES (...);

-- при входе
SELECT * FROM users WHERE email = ?;

-- проверка дубликата
SELECT EXISTS(SELECT 1 FROM users WHERE email = ?);
```

Hibernate `ddl-auto: update` создаёт и обновляет схему при старте контейнера.

**Redis — refresh-токены**

`RefreshTokenService` использует две структуры:

- ключ = сам refresh-токен, значение = email, TTL 7 дней;
- множество `user_tokens:<email>` — все активные refresh пользователя для массового отзыва при новом входе.

Операции: `SET`, `SADD`, `EXPIRE`, `DEL` — через `RedisTemplate<String, String>`.

### 3.3.4. Обработка ошибок

`GlobalExceptionHandler` возвращает JSON `ApiErrorResponse` с кодами **400** (валидация), **401** (неверные учётные данные / refresh), **409** (email занят).

#### Детализация сценариев auth-service

**Регистрация (рис. 3.11).** После `save(user)` генерируются оба токена; refresh сразу помещается в Redis. Клиент получает UUID в claim access-токена — этот идентификатор далее используется во всех сервисах как `user_id`.

**Выход (рис. 3.12).** Logout идемпотентен: повторный вызов с тем же refresh не приводит к ошибке. Отозванный refresh не проходит проверку `isValid` при попытке обновления access.

**Refresh (рис. 3.13).** Access перевыпускается, refresh остаётся прежним (ротация refresh при необходимости может быть добавлена отдельной задачей). Срок access 15 минут стимулирует частое обновление без повторного ввода пароля.

**Классы (рис. 3.14).** Связи Controller → Service → Repository соответствуют слоям Spring. `JwtService` и `RefreshTokenService` вынесены для соблюдения SRP и упрощения модульных тестов (`JwtServiceTest`, `AuthServiceTest`).

**Безопасность паролей.** `SecurityConfig` регистрирует `BCryptPasswordEncoder` strength 10. Пароль никогда не логируется и не возвращается в API.

## 3.4. Разработка сервиса пользовательских данных (user-service)

### 3.4.1. Назначение модуля

**user-service** — крупнейший модуль комплекса. Хранит медицинский профиль, дневник питания, симптомы, самочувствие, лекарства и справочники. API размещено под префиксом `/api/**`; идентификатор пользователя не передаётся клиентом в теле запроса — он извлекается из заголовка **`X-User-Id`**, установленного шлюзом.

Защита от прямого доступа: фильтр **`InternalGatewayFilter`** проверяет **`X-Internal-Gateway-Token`** (общий секрет с gateway и analytics). Без корректного токена возвращается **401**.

Резолвер **`UserIdArgumentResolver`** + аннотация `@CurrentUserId` подставляют UUID в параметры контроллеров.

### 3.4.2. Структура пакетов и основные классы

| Пакет / модуль | Ключевые классы | Функция |
|----------------|-----------------|---------|
| `userInfo` | `FoodIntakeController`, `FoodIntakeService`, документы MongoDB | Дневник питания |
| `symptoms` | `SymptomController`, `SymptomServiceImpl` | Симптомы (справочник PG + записи Mongo) |
| `medicines` | `MedicineController`, `IntakeMedicineController` | Лекарства и приёмы |
| `food` | `FoodController`, `FoodServiceImpl` | Справочник продуктов и компонентов |
| `foodanalyzer` | `FoodAnalyzerController`, `FoodAnalyzerServiceFacade` | Корреляция «компонент еды — симптом» |
| `config` | `SecurityConfig`, `MongoConfig`, `WebConfig` | Безопасность и MVC |

Пример REST для дневника (`FoodIntakeController`):

- `POST /api/feelings/food` — создание приёма пищи;
- `GET /api/feelings/food` — выборка по дате;
- `PUT` / `DELETE` — изменение и удаление записей.

Пищевой анализатор (`GET /api/food-analyzer/analyze?from=&to=`) возвращает список `FoodComponentSymptomsResponse` — компоненты, после которых в «окне риска» фиксировались симптомы.

### 3.4.3. Реализация пищевого анализатора

`FoodAnalyzerServiceFacade` агрегирует данные из MongoDB (приёмы пищи, симптомы за период) и PostgreSQL (состав продуктов `food` / `food_components`). Алгоритм в `FoodComponentAnalyzerServiceImpl`:

1. выбрать все приёмы пищи пользователя в интервале `[from, to]`;
2. для каждого компонента продукта определить, были ли симптомы в заданном интервале после приёма;
3. сформировать DTO с именем компонента и списком связанных симптомов.

Результат используется **analytics-service** при формировании PDF-отчёта.

### 3.4.4. Обращения к базам данных

**PostgreSQL (`user_pg`)**

Таблицы: `food`, `food_components`, `symptom`, `medicine`, `intake_medicine`. Связь с пользователем — поле `user_id` (UUID из auth-service, без FK на другую БД).

Примеры запросов уровня приложения:

```sql
SELECT f.* FROM food f WHERE f.user_id = :userId;
SELECT fc.* FROM food_components fc WHERE fc.food_id = :foodId;
SELECT m.* FROM medicine m WHERE m.user_id = :userId;
SELECT im.* FROM intake_medicine im
  WHERE im.user_id = :userId AND im.intake_date BETWEEN :from AND :to;
```

**MongoDB (`health_tracker`)**

Коллекции: `user_info`, `food_intakes`, `symptoms`, `common_feelings`, `notes`. Доступ через репозитории `MongoRepository` / `MongoTemplate`. Пример логики:

```javascript
db.food_intakes.find({
  userId: UUID("..."),
  intakeDate: { $gte: ISODate("..."), $lte: ISODate("...") }
})
```

Документ `user_info` содержит вложенные списки аллергенов, хронических заболевений, антропометрию — структура гибко расширяется без миграций SQL.

## 3.5. Разработка сервиса аналитики (analytics-service)

### 3.5.1. Назначение модуля

**analytics-service** формирует **медицинский PDF-отчёт** за период. Точка входа — `ReportController` (`@RequestMapping("/reports")`):

- `GET /reports/generate?from=&to=` — сбор данных, JasperReports, ответ `application/pdf`;
- `GET /reports/download` — PDF из переданного `ReportDataDto` (без повторного Feign).

Пользователь определяется атрибутом `currentUserId`, установленным `InternalGatewayFilter` из заголовка `X-User-Id`.

### 3.5.2. Классы и взаимодействие

| Класс | Роль |
|-------|------|
| `ReportController` | REST-слой |
| `ReportService` | `fillReport`, `generateMedicalReport`, `transformToAnalysis` |
| `UserServiceClient` | Feign-клиент к `http://gateway-service:8080` |
| `FeignConfig` | Проброс `X-User-Id` и `X-Internal-Gateway-Token` |
| `JasperConfig` | Компиляция шаблона `medical_report.jrxml` |
| `MedicalReport` / `MedicalReportRepository` | Сохранение PDF в `report_pg` |
| `ReportDataProducer` | Публикация в Kafka |
| `AiAnalysisConsumer` | Потребление топика, вызов GigaChat |
| `GigaChatService` | Формирование промпта и `AnalysisResultDto` |

Метод **`ReportService.fillReport`** выполняет цепочку Feign-запросов:

1. `GET /api/user/info` → профиль;
2. `GET /api/feelings/medicines?from&to` → лекарства;
3. `GET /api/feelings/common?from&to` → самочувствие;
4. `GET /api/food-analyzer/analyze?from&to` → корреляции.

Далее `transformToAnalysis` агрегирует уникальные продукты и симптомы; при включённом AI-контуре обогащение выполняется через Kafka → GigaChat.

**`generateMedicalReport`** использует `JasperFillManager.fillReport` с `JRBeanCollectionDataSource` и шаблоном отчёта (логотип, таблицы лекарств, график самочувствия, текст заключения).

### 3.5.3. Асинхронный контур Kafka и GigaChat

Топик **`report-data-requests`** принимает сериализованный `ReportDataDto`. Producer вызывается после первичного наполнения отчёта; Consumer асинхронно запрашивает **GigaChat API** (модель GigaChat, OAuth scope `GIGACHAT_API_PERS`) и дополняет поле `analysis` рекомендациями врача.

Преимущества реализации:

- генерация PDF не блокируется на время ответа LLM;
- повторная обработка сообщений при сбоях (политика consumer group);
- горизонтальное масштабирование consumer-инстансов.

### 3.5.4. Запросы к PostgreSQL

Таблица **`medical_reports`** (сущность `MedicalReport`):

| Поле | Тип | Назначение |
|------|-----|------------|
| id | BIGSERIAL | PK |
| user_id | UUID | Владелец отчёта |
| created_at | TIMESTAMP | Время создания |
| status | VARCHAR | Статус (NEW, READY, …) |
| pdf_content | BYTEA | Бинарное тело PDF |

```sql
INSERT INTO medical_reports (user_id, created_at, status, pdf_content)
VALUES (:userId, :createdAt, :status, :pdfBytes);

SELECT * FROM medical_reports WHERE user_id = :userId ORDER BY created_at DESC;
```

Индекс `idx_mr_user_id` ускоряет выборку истории отчётов пользователя.

## 3.6. Разработка сервиса сканирования (scan-service)

### 3.6.1. Назначение модуля

**scan-service** анализирует **фото этикетки** (состав продукта) с помощью **GigaChat Vision**, загружает медицинский профиль пользователя через **Feign → gateway → user-service** и возвращает структурированный ответ для UI: какие компоненты **безопасны**, какие требуют **осторожности**, какие **опасны** с кратким обоснованием.

Сервис развёрнут на **VPS** в Docker; снаружи доступен **только через API Gateway** (`POST /scan/analyze`, multipart). Порт scan-service не публикуется в интернет.

### 3.6.2. Реализованные классы

| Класс | Ответственность |
|-------|-----------------|
| `ScanController` | `POST /scan/analyze` — приём изображения |
| `ScanService` | Оркестрация: профиль → GigaChat → классификация |
| `GigaChatVisionService` | Vision API: извлечение списка ингредиентов из фото |
| `PromptBuilder` | Промпт с требованием JSON-ответа |
| `IngredientSafetyService` | Сопоставление с `allergies`, `predisposition`, `chronicDiseases` |
| `UserProfileClient` | Feign: `GET /api/user/info` через `gateway-service:8080` |
| `FeignConfig` / `InternalGatewayFilter` | Заголовки `X-User-Id`, `X-Internal-Gateway-Token` |

Ответ `ComponentAnalysisResponse` содержит три группы: `safe`, `caution`, `unsafe` (enum `SafetyLevel`) и поле `summary` для экрана приложения.

### 3.6.3. Хранение данных

Основной сценарий **stateless** (без обязательной БД). Опционально на VPS можно вести таблицу `label_scan_history` (JSON результата, `user_id`, `scanned_at`) — см. рис. 2.53.

#### Сценарии scan-service по диаграммам

## 3.7. Реализация пользовательского интерфейса

Клиентское приложение (мобильное или web) реализует сценарии, описанные в вариантах использования микросервисов. Взаимодействие — **HTTPS + JSON** (для scan — `multipart/form-data`) только с **gateway-service:8080**.

Полное описание структуры UI — в документе [`docs/СТРУКТУРА_ПОЛЬЗОВАТЕЛЬСКОГО_ИНТЕРФЕЙСА.md`](СТРУКТУРА_ПОЛЬЗОВАТЕЛЬСКОГО_ИНТЕРФЕЙСА.md). Ниже — краткое изложение для главы 3.

### 3.7.1. Структура пользовательского интерфейса

Интерфейс разделён на **неавторизованную зону** (вход, регистрация) и **основное приложение** с нижней панелью из пяти вкладок:

1. **Главная** — дашборд за текущий день, быстрые действия;  
2. **Дневник** — приёмы пищи, симптомы, самочувствие, лекарства, заметки;  
3. **Анализ** — пищевой анализатор (триггеры за период), формирование PDF-отчёта;  
4. **Сканер** — фото этикетки, результат в трёх группах (безопасно / осторожно / опасно);  
5. **Профиль** — медицинские данные, аллергены, предрасположенность.

**ВСТАВИТЬ РИСУНОК 3.41** — `docs/uml/plantuml/ui/01-ui-navigation-structure.puml`  
*Подпись:* «Рисунок 3.41 — Структура навигации клиентского приложения».

Внутри модуля «Дневник» используется вторичная навигация (вкладки). Модуль «Сканер» — линейный поток: камера → загрузка → экран результата с цветовой кодировкой `safe` / `caution` / `unsafe` и полем `summary`.

### 3.7.2. Связь экранов с API

| Раздел UI | Ключевые endpoint |
|-----------|-------------------|
| Вход / регистрация | `/auth/login`, `/auth/register`, `/auth/logout`, `/auth/refresh` |
| Профиль | `GET/PUT /api/user/info` |
| Дневник | `/api/feelings/food`, `/symptoms`, `/common`, `/medicines`, `/notes` |
| Анализ | `/api/food-analyzer/analyze`, `/reports/generate` |
| Сканер | `POST /scan/analyze` |

### 3.7.3. Хранение токенов и сессии на клиенте

После входа клиент сохраняет **access** (15 мин) и **refresh** (7 суток) в защищённом хранилище. Access передаётся в `Authorization: Bearer …` при запросах к `/api/**`, `/reports/**`, `/scan/**`. При **401** выполняется `/auth/refresh` и повтор исходного запроса.

### 3.7.4. Визуализация результата сканирования

Экран результата разбит на три списка по полям `ComponentAnalysisResponse`: зелёная зона (`safe`), оранжевая (`caution`), красная (`unsafe`). Для доступности дублируется текстовая метка уровня риска, не только цвет.

## 3.8. Сборка, контейнеризация и развёртывание

Каждый микросервис содержит `Dockerfile` и `docker-compose.yml`. Типовой образ: multi-stage build (Maven → JRE 17). Переменные окружения: `JWT_SECRET`, `INTERNAL_SECRET`, `SPRING_DATASOURCE_*`, адреса Kafka и GigaChat.

Сетевая топология (обобщённо по диаграммам развёртывания 3.8, 3.16, 3.24, 3.32, 3.40):

- клиент → **gateway:8080**;
- gateway → auth / user / analytics / scan;
- analytics → gateway (Feign) → user;
- auth → PostgreSQL + Redis;
- user → PostgreSQL + MongoDB;
- analytics → PostgreSQL + Kafka → GigaChat;
- scan → GigaChat Vision; Feign → gateway → user.

## 3.1. Общая характеристика этапа разработки

На этапе разработки программный комплекс Product-allergen был реализован в виде пяти микросервисов, спроектированных в главе 2. Каждый сервис представляет собой отдельный Maven-модуль, разработанный на языке **Java 17** с использованием **Spring Boot 3.x**, упакованный в Docker-образ и развёрнутый в общей Docker-сети **backend-net**.

Результатом разработки является функционирующее программное решение, включающее:

- REST API, доступное клиентскому приложению через единый шлюз **gateway-service** (порт 8080);
- систему хранения данных на базе **PostgreSQL**, **MongoDB** и **Redis**;
- асинхронный контур обработки отчётов на **Apache Kafka** (analytics-service);
- интеграцию с **GigaChat** для текстового анализа медицинских отчётов и распознавания состава по фото этикетки (scan-service);
- клиентское мобильное и веб-приложение на **React Native (Expo)**, обращающееся к API только через шлюз.

Клиент не обращается к микросервисам напрямую: все запросы проходят через gateway, что упрощает безопасность и смену адресов сервисов при развёртывании.

## 3.2. Разработка API Gateway (gateway-service)

### 3.2.1. Назначение

Микросервис **gateway-service** реализует функцию единой точки входа в программный комплекс. Сервис разработан на основе **Spring Cloud Gateway 2023.0.4** и **Spring Boot 3.3.6**, использует реактивный стек **Spring WebFlux** и слушает порт **8080**.

Основные задачи:

- маршрутизация HTTP-запросов к auth-service, user-service, analytics-service и scan-service;
- централизованная проверка JWT access-токена для защищённых префиксов;
- добавление служебных заголовков `X-User-Id` и `X-Internal-Gateway-Token` для downstream-сервисов;
- глобальная настройка CORS для браузерного и мобильного клиента;
- исключение прямого доступа клиента к внутренним портам микросервисов.

Gateway не содержит предметной логики аллергий и не обращается к базам данных.

### 3.2.2. REST API и маршрутизация

Собственного REST API у gateway нет: он проксирует запросы по правилам из `application.yml`. Ниже приведена фактическая таблица маршрутов (файл `gateway/src/main/resources/application.yml`).

| ID маршрута | Predicate (путь клиента) | Целевой URI | Фильтр JWT |
|-------------|--------------------------|-------------|------------|
| `auth_route` | `/auth/**` | `http://auth-service:8080` | нет |
| `user_route` | `/api/**` | `http://user-service:8080` | `AuthenticationFilter`, `skipAuth: false` |
| `analytics_route` | `/reports/**` | `http://analytics-service:8080` | `AuthenticationFilter`, `skipAuth: false` |
| `scan_route` | `/scans/**` | `http://scan-service:8080` | `AuthenticationFilter`, `skipAuth: false` |

Имена хостов (`auth-service`, `user-service` и т.д.) соответствуют именам контейнеров в Docker-сети **backend-net**.

**Обработка защищённого запроса** выполняется фильтром `AuthenticationFilter` (`ru.productallergen.gateway.filter`):

1. Из заголовка `Authorization` извлекается значение `Bearer <access_token>`.
2. Класс `JwtUtils` проверяет подпись HS256, срок действия и claim `type` (ожидается `access`).
3. Из claim `id` извлекается UUID пользователя.
4. К запросу добавляются заголовки:
   - `X-User-Id` — идентификатор пользователя;
   - `X-Internal-Gateway-Token` — значение `internal.api.secret` (секрет доверия между шлюзом и сервисами).
5. Модифицированный запрос передаётся в целевой микросервис.

При отсутствии заголовка `Authorization`, неверном формате или невалидном токене gateway возвращает **HTTP 401 Unauthorized** и не вызывает downstream-сервис.

**Публичные маршруты** `/auth/**` обслуживают регистрацию, вход, обновление и отзыв токенов без участия `AuthenticationFilter`.

**CORS** настроен глобально (`spring.cloud.gateway.globalcors`):

- `allowedOriginPatterns: "*"` (для разработки и Expo);
- методы GET, POST, PUT, DELETE, OPTIONS;
- `allowedHeaders: "*"`, `allowCredentials: true`.

Это позволяет web-клиенту и инструментам разработки выполнять preflight-запросы OPTIONS перед основным вызовом API.

**Конфигурация JWT** в gateway согласована с auth-service:

- `jwt.secret` ← переменная окружения `JWT_SECRET`;
- `jwt.claim.id: id`, `jwt.claim.type: type`.

## 3.3. Разработка сервиса аутентификации (auth-service)

### 3.3.1. Назначение

Микросервис **auth-service** реализует регистрацию, вход, обновление access-токена и выход пользователя. Сервис построен на **Spring Boot 3.2.4**, **Spring Security** и не хранит медицинские данные.

Функции:

- создание учётной записи с хешированием пароля (**BCrypt**);
- аутентификация через `AuthenticationManager`;
- выпуск пары JWT (access + refresh);
- хранение действительных refresh-токенов в **Redis** с возможностью отзыва;
- единый формат ошибок API (`ApiErrorResponse`).

Все методы доступны клиенту по префиксу **`/auth/**`** через gateway без проверки JWT на шлюзе; валидация выполняется внутри auth-service.

### 3.3.2. REST API

Контроллер `AuthController` (`@RequestMapping("/auth")`) предоставляет следующие endpoints:

| HTTP | URL | Тело запроса | Ответ | Назначение |
|------|-----|--------------|-------|------------|
| POST | `/auth/register` | `RegisterRequest` | `AuthResponse` | Регистрация |
| POST | `/auth/login` | `LoginRequest` | `AuthResponse` | Вход |
| POST | `/auth/refresh` | `RefreshRequest` | `AuthResponse` | Новый access (refresh без ротации строки) |
| POST | `/auth/logout` | `LogoutRequest` | `String` | Отзыв refresh в Redis |

**DTO:**

- `LoginRequest`, `RegisterRequest`: `email` (валидация @Email), `password` (не менее 6 символов, латиница/цифры/спецсимволы);
- `AuthResponse`: `accessToken`, `refreshToken`;
- `RefreshRequest`, `LogoutRequest`: поле `refreshToken`.

**Коды ошибок** (через `GlobalExceptionHandler`):

| HTTP | Ситуация |
|------|----------|
| 400 | Ошибка валидации полей |
| 401 | Неверный email/пароль, невалидный refresh |
| 409 | Email уже зарегистрирован |

### 3.3.3. Структура классов

| Слой | Классы | Роль |
|------|--------|------|
| controller | `AuthController` | REST-адаптер |
| service | `AuthService` | Регистрация, login, refresh, logout |
| service | `RefreshTokenService` | Redis: save / isValid / revoke / revokeOldTokensByEmail |
| security | `JwtService` | Генерация и разбор JWT (HS256) |
| entity | `User` | JPA-сущность, `UserDetails` |
| repository | `UserRepository` | `JpaRepository<User, UUID>` |
| config | `SecurityConfig` | Stateless, `AuthenticationManager`, BCrypt |
| exception | `GlobalExceptionHandler`, доменные исключения | Единый JSON ошибок |

**JwtService** формирует токены с claims:

- `sub` — email;
- `id` — UUID пользователя (только access);
- `type` — `access` или `refresh`.

**Сроки действия** (по умолчанию в `application.yml`):

- access — **900 000 мс (15 минут)** (`JWT_ACCESS_EXPIRATION`);
- refresh — **604 800 000 мс (7 суток)** (`JWT_REFRESH_EXPIRATION`).

**RefreshTokenService** использует две структуры Redis:

1. ключ `<refreshToken>` → значение `<email>`, TTL 7 суток;
2. множество `user_tokens:<email>` → список активных refresh для отзыва при новом входе.

**Сущность User** (таблица `users`): `id` (UUID), `email` (unique), `password` (BCrypt), `is_active`, `created_at`, `updated_at`.

## 3.4. Разработка сервиса пользовательских данных (user-service)

### 3.4.1. Назначение

**user-service** — центральный модуль хранения медицинских и поведенческих данных пользователя: профиль, дневник питания, симптомы, лекарства, заметки, справочники продуктов и анализ пищевых триггеров.

Особенности реализации:

- **полиглотное хранение**: MongoDB для гибких документов дневника и профиля; PostgreSQL для справочников и нормализованных связей;
- идентификатор пользователя **не передаётся в теле** защищённых запросов — извлекается из заголовка `X-User-Id`, установленного gateway;
- фильтр **InternalGatewayFilter** отклоняет запросы без корректного `X-Internal-Gateway-Token`;
- резолвер **UserIdArgumentResolver** и аннотация **@CurrentUserId** подставляют `UUID` в параметры контроллеров.

Все REST-методы для клиента имеют префикс **`/api/**`**.

#### Обращения к базам данных (примеры)

**PostgreSQL** — справочники и привязка к пользователю через `user_id`:

```sql
-- продукты пользователя
SELECT f.* FROM food f WHERE f.user_id = :userId;

-- компоненты продукта (через JPA ElementCollection)
SELECT fc.* FROM food_components fc WHERE fc.food_id = :foodId;

-- история приёма лекарств за период
SELECT im.* FROM intake_medicine im
WHERE im.user_id = :userId
  AND im.intake_date BETWEEN :from AND :to;
```

**MongoDB** — дневник за день или период:

```javascript
db.food_intakes.find({
  userId: UUID("..."),
  intakeDate: { $gte: ISODate("..."), $lte: ISODate("...") }
});
```

Параметр `spring.jpa.hibernate.ddl-auto=update` в user-service обеспечивает автоматическое обновление схемы PostgreSQL при развёртывании; для MongoDB схема коллекций определяется структурой документов.

#### Механизм доверия к gateway

`InternalGatewayFilter` наследует `OncePerRequestFilter` и для всех путей, кроме Swagger (`/swagger-ui`, `/v3/api-docs`), сравнивает заголовок `X-Internal-Gateway-Token` с `internal.api.secret`. Это предотвращает обращение к user-service в обход gateway даже при знании внутреннего DNS-имени контейнера. Идентификатор пользователя извлекается **только** из `X-User-Id`, установленного шлюзом после проверки JWT — клиент не может подменить чужой `userId` в теле запроса.

## 3.5. Разработка сервиса аналитики (analytics-service)

### 3.5.1. Назначение

**analytics-service** формирует медицинские аналитические отчёты: собирает данные пользователя через OpenFeign, обогащает их рекомендациями **GigaChat**, сохраняет снимок отчёта в PostgreSQL и отдаёт **PDF**, сгенерированный **JasperReports**.

Задачи:

- агрегация профиля, дневника, лекарств и результатов food-analyzer за период;
- baseline-анализ на основе корреляций продуктов и симптомов;
- асинхронный (с fallback) вызов GigaChat через Kafka;
- хранение истории отчётов в таблице `report_snapshots` (JSONB);
- выдача PDF клиенту и повторная загрузка по `snapshotId`.

### 3.5.2. REST API

Контроллер `ReportController` (`/reports`):

| HTTP | URL | Назначение |
|------|-----|------------|
| GET | `/reports/generate?from=&to=` | Сбор данных, AI-обогащение, сохранение snapshot, ответ PDF (`medical_analysis_full.pdf`), заголовок `X-Report-Snapshot-Id` |
| GET | `/reports/snapshots` | Список снимков отчётов пользователя |
| GET | `/reports/snapshots/{snapshotId}` | JSON `ReportDataDto` |
| GET | `/reports/snapshots/{snapshotId}/pdf` | PDF из сохранённого snapshot |
| POST | `/reports/download` | PDF из переданного в теле `ReportDataDto` (без повторного Feign/AI) |

Идентификатор пользователя передаётся через `@RequestAttribute("currentUserId")` после обработки `InternalGatewayFilter` (аналогично user-service: заголовки от gateway).

### 3.5.3. Реализация формирования PDF

Цепочка в `ReportService`:

1. **`collectReportData(from, to)`** — последовательные вызовы Feign-клиента `UserServiceClient` (базовый URL `http://gateway-service:8080`):
   - GET `/api/user/info` — профиль;
   - GET `/api/feelings/medicines` — приёмы лекарств за период;
   - GET `/api/feelings/common` — самочувствие;
   - GET `/api/food-analyzer/analyze` — пищевые триггеры.
2. **`reportAiEnricher.enrichViaKafka(...)`** — публикация `ReportDataDto` в топик `report-ai-requests`, ожидание ответа в `ReportAiRegistry` (таймаут **90 с**), при сбое — прямой вызов `GigaChatAnalysisService`.
3. **`reportSnapshotService.save(...)`** — запись в `report_snapshots` (поле `report_data` типа JSONB).
4. **`generateMedicalReport(data)`** — Jasper:
   - шаблон `templates/medical_report.jrxml` (bean `JasperReport` в `JasperConfig`);
   - источник данных `JRBeanCollectionDataSource` с единственным элементом `ReportDataDto`;
   - `JasperFillManager.fillReport` + `JasperExportManager.exportReportToPdf`.

PDF включает персональные данные, таблицы лекарств и симптомов, блок анализа (`AnalysisResultDto`: продукты, симптомы, опасные белки, микроэлементы, текст рекомендации).

**Kafka-контур:**

| Топик | Роль |
|-------|------|
| `report-ai-requests` | Producer из `ReportAiOrchestrator`, Consumer `ReportAiKafkaConsumer` |
| `report-ai-results` | Публикация результата (синхронизация через in-memory registry) |

Consumer вызывает `GigaChatAnalysisService.enrichReport`: сначала baseline `ReportAnalysisMapper.fromFoodSymptoms`, затем текстовый completion GigaChat (модель по умолчанию **GigaChat-2-Max**), парсинг JSON, методы `fillMissingProteinAndTrace` и `supplementProteinAndTrace`.

**Конфигурация GigaChat** (`GigaChatConfig`, `gigachat-java` 0.1.14):

- `GIGACHAT_AUTH_KEY` → OAuth scope `GIGACHAT_API_PERS`;
- `GIGACHAT_MODEL` (не использовать внутренние имена SDK вроде `GIGA_CHAT_MAX_2` — только API-id);
- при пустом ключе bean `GigaChatClient` не создаётся, отчёт остаётся на baseline.

> В дипломе не следует указывать `GIGACHAT_CLIENT_ID` / `GIGACHAT_CLIENT_SECRET` — в реализации используется **единый auth key** `GIGACHAT_AUTH_KEY`, как в scan-service.

### 3.5.4. Структура классов

| Пакет / класс | Назначение |
|---------------|------------|
| `ReportController` | REST API отчётов |
| `ReportService` | Сбор данных, PDF, оркестрация |
| `ReportSnapshotService` | CRUD снимков |
| `ReportAiOrchestrator`, `ReportAiKafkaProducer`, `ReportAiKafkaConsumer`, `ReportAiRegistry` | Kafka + ожидание |
| `GigaChatAnalysisService` | Вызов GigaChat, парсинг |

Сущность `MedicalReport` (таблица `medical_reports` с полем `pdf_content`) сохранена в модели данных, но основной рабочий путь использует **`ReportSnapshot`**.

**Таблица `report_snapshots`** (основное хранилище):

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | BIGSERIAL | Идентификатор снимка |
| `user_id` | UUID | Владелец отчёта |
| `period_from`, `period_to` | DATE/TIMESTAMP | Период анализа |
| `created_at` | TIMESTAMP | Время создания |
| `report_data` | JSONB | Сериализованный `ReportDataDto` (включая `analysis`) |

Повторная выдача PDF по `snapshotId` не требует повторного вызова GigaChat — данные читаются из JSONB и прогоняются через Jasper.

**Эвристики `ReportAnalysisMapper`** (фрагмент логики для диплома): по названию продукта из дневника выводятся маркеры аллергенных белков — например, при вхождении подстрок «молок», «сыр» добавляются «Казеин», «β-лактоглобулин»; при «глютен», «пшен» — «Глиадин», «Глютенин»; при «арахис» — «Ara h 1», «Ara h 2». Аналогично заполняются микроэлементы. После ответа GigaChat методы `fillMissingProteinAndTrace` и `supplementProteinAndTrace` гарантируют непустые списки, если модель вернула неполный JSON.

## 3.6. Разработка сервиса сканирования (scan-service)

### 3.6.1. Назначение

**scan-service** анализирует **фотографию этикетки** продукта: распознаёт состав, сопоставляет его с медицинским профилем пользователя и возвращает структурированный результат для UI (уровень риска, список ингредиентов, опасные компоненты, клиническая заметка).

Сервис разработан на **Spring Boot 3.x**, взаимодействует с user-service через **OpenFeign** (через gateway) и использует **GigaChat Vision** (загрузка файла + completion с вложением).

По умолчанию:

- **Kafka отключён** (`SCAN_KAFKA_ENABLED=false`) — изображение в Base64 превышает лимит сообщения Kafka (~1 МБ);
- **PostgreSQL опционален** (`SCAN_PERSISTENCE_ENABLED=false`) — история сканов в памяти до рестарта контейнера.

### 3.6.2. REST API

Контроллер `ScanController` (префикс **`/scans`**, не `/scan`):

| HTTP | URL | Назначение |
|------|-----|------------|
| POST | `/scans/analyze` | `multipart/form-data`, поле **`image`** (обязательно), max 10 MB |
| GET | `/scans/{scanId}` | Получение результата по id |
| GET | `/scans/history` | История сканов текущего пользователя |

Доступ только через gateway: маршрут **`/scans/**`** с `AuthenticationFilter`.

Ответ содержит `scanId` и объект `analysis` (`ScanAnalysisResultDto`):

- `productName`;
- `composition` — список ингредиентов;
- `dangerousComponents` — компоненты риска для данного пользователя;
- `riskLevel` — `LOW` / `MEDIUM` / `HIGH` / `UNKNOWN`;
- `clinicalNoteForDoctor` — текст для отображения в блоке «Рекомендация» в приложении.

### 3.6.3. Интеграция с GigaChat Vision

Реализация сосредоточена в **`GigaChatScanService`** и конфигурации **`GigaChatConfig`** (идентичный принцип OAuth, что и в analytics-service).

**Алгоритм вызова:**

1. Проверка наличия bean `GigaChatClient` и непустого `GIGACHAT_AUTH_KEY`.
2. Декодирование изображения (из multipart или Base64 в Kafka-сообщении).
3. **`uploadFile`** — загрузка байтов в GigaChat (`mimeType`, `fileName`, `purpose=general`).
4. **`completions`** — модель из `GIGACHAT_MODEL` (по умолчанию `GigaChat-2-Max`), сообщение пользователя с **attachment** = id загруженного файла.
5. Промпт (`buildPrompt`) требует ответ **строго в JSON**: `productName`, `composition[]`, `dangerousComponents[]`, `riskLevel`, `clinicalNoteForDoctor`; в промпт сериализуется **`UserInfoDto`** (аллергии, хронические заболевания и др.).
6. **`parseResponse`** — извлечение JSON из текста ответа, маппинг в `ScanAnalysisResultDto`.

**Оркестрация** — класс **`ScanAiOrchestrator`**:

- при `scan.kafka.enabled=true` и размере файла ≤ `max-image-bytes-for-kafka` (400 000 байт) — публикация в `scan-ai-requests`, ожидание в `ScanAiRegistry` (120 с);
- иначе — **прямой вызов** `GigaChatScanService` в потоке HTTP-запроса (режим по умолчанию в продуктиве).

Топики: `scan-ai-requests`, `scan-ai-results`. Consumer `ScanAiKafkaConsumer` вызывает тот же `GigaChatScanService`.

### 3.6.4. Алгоритм оценки аллергенов и уровня риска

В scan-service **нет отдельного Java-класса с правилами сопоставления каждого ингредиента с аллергеном** — оценка выполняется **моделью GigaChat** на основе:

- распознанного списка `composition`;
- профиля пользователя (`UserInfoDto`: перечень аллергий, предрасположенностей, хронических заболеваний);
- инструкций в промпте выделить `dangerousComponents` и задать `riskLevel`.

**Уровни риска** (`riskLevel`), возвращаемые API:

| Значение | Смысл для клиента |
|----------|-------------------|
| LOW | Низкий риск для профиля |
| MEDIUM | Средний риск |
| HIGH | Высокий риск |
| UNKNOWN | Не удалось классифицировать (ошибка ИИ, пустой ключ, сбой парсинга) |

Клиентское приложение (`scanApi.ts`, экран `scan.tsx`) преобразует `riskLevel` и долю `dangerousComponents` в **оценку 0–100** и цветовую метку («Низкий / Средний / Высокий риск»).

**Сравнение с analytics-service:** там дополнительно к AI применяется **детерминированный** слой `ReportAnalysisMapper` — эвристики `inferDangerousProteins` и `inferTraceElements` по ключевым словам в названиях продуктов (молоко → казеин, глютен → глиадин и т.д.). Этот слой используется для **отчётов за период**, а не для разового сканирования этикетки.

**Загрузка профиля:** `UserProfileLoader` / Feign `UserServiceClient.getUserInfo()` → GET `/api/user/info`. При недоступности профиля сервис продолжает анализ с пустым или частичным профилем (логирование предупреждения).

## 3.7. Разработка клиентского приложения

Клиентская часть комплекса реализована как кроссплатформенное приложение **React Native** с фреймворком **Expo** (репозиторий Product-allergen-frontend). Навигация построена на **Expo Router** (`app/(tabs)/`): четыре основные вкладки — дневник, камера (сканер), отчёты, профиль.

### 3.7.1. Взаимодействие с backend

Базовый URL API задаётся в `src/api/config.ts` (`API_BASE_URL`) и указывает на **gateway-service** (порт 8080), а не на отдельные микросервисы.

| Модуль клиента | Префикс API | Соответствие сервису |
|----------------|-------------|----------------------|
| `authApi.ts` | `/auth/*` | auth-service |
| `diaryApi.ts`, `profileApi.ts` | `/api/*` | user-service |
| `reportsApi.ts` | `/reports/*` | analytics-service |
| `scanApi.ts` | `/scans/*` | scan-service |

Access-токен хранится в `AsyncStorage` и передаётся в заголовке `Authorization: Bearer ...` для всех защищённых запросов. При истечении срока действия выполняется обновление через `/auth/refresh`.

### 3.7.2. Экран сканирования этикетки

Файл `app/(tabs)/scan.tsx` реализует сценарий:

1. Запрос разрешения камеры (`expo-camera`);
2. Съёмка этикетки (`takePictureAsync`, качество 0.85);
3. Автоматическая отправка `FormData` с полем `image` на `POST /scans/analyze` (таймаут до 180 с);
4. Отображение `ScanAnalysisResult`: оценка 0–100, цвет уровня риска, чипы ингредиентов, список опасных компонентов, блок рекомендации (`clinicalNoteForDoctor`).

Маппинг ответа сервера выполняется в `mapScanAnalysisDto` (`scanApi.ts`): уровни `LOW` / `MEDIUM` / `HIGH` преобразуются в пользовательские подписи и цвета UI.

Для веб-сборки и отладки предусмотрен локальный путь OCR (`src/ocr/labelOcr.ts`, `ingredientParser.ts`, `ingredientSafety.ts`) — анализ текста без сервера; в мобильной сборке основной сценарий — серверный анализ через scan-service.

### 3.7.3. Дневник и отчёты

Экран дневника (`diary.tsx`) агрегирует CRUD-операции к `/api/feelings/*` и справочникам. Экран отчётов запрашивает генерацию PDF через `/reports/generate` и сохраняет/открывает файл средствами `expo-file-system` и `expo-sharing`.

Таким образом, клиентское приложение завершает сквозной сценарий комплекса: аутентификация → накопление данных в user-service → аналитика и сканирование → представление результата пользователю.

## Заключение по главе 3

В результате разработки реализован распределённый программный комплекс из пяти микросервисов и клиентского приложения. **gateway-service** обеспечивает единый периметр безопасности; **auth-service** — JWT и Redis; **user-service** — полиглотное хранение медицинских данных; **analytics-service** — PDF-отчёты и AI-анализ через Kafka и GigaChat; **scan-service** — персонализированный анализ состава по фото этикетки с GigaChat Vision. Все сервисы согласованы по внутреннему заголовку `X-Internal-Gateway-Token` и идентификатору пользователя `X-User-Id`, что соответствует проектным решениям главы 2 и обеспечивает согласованную эксплуатацию в Docker-среде **backend-net**.

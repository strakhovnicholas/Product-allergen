# ГЛАВА 4. ТЕСТИРОВАНИЕ ПРОГРАММНОЙ СИСТЕМЫ

В данной главе описан план тестирования программного комплекса **Product-allergen**, применённые инструментальные средства, реализованные автоматизированные проверки и ручные сценарные тесты. Цель тестирования — убедиться в работоспособности ключевых микросервисов, корректности бизнес-логики аутентификации и ведения дневника, а также в согласованности сквозных сценариев: вход в систему → накопление медицинских данных → формирование отчёта и анализ состава продукта по фото этикетки.

---

## 4.1. План тестирования

План тестирования разработан в соответствии с **моделью тестовой пирамиды** и предполагает три уровня проверки качества — от наиболее объёмного и быстрого к наиболее затратному.

**ВСТАВИТЬ РИСУНОК 4.1**  
*Подпись:* «Рисунок 4.1 — Пирамида тестирования программного комплекса Product-allergen».

**Нижний уровень — юнит-тесты и узкие интеграционные тесты контроллеров.** Наиболее быстрые автоматизированные проверки, выполняемые без полного развёртывания Docker-стека. В проекте они реализованы для **auth-service** (изолированные Mockito-тесты сервиса и JWT) и **user-service** (тесты анализатора пищевых триггеров, мапперов и части REST-контроллеров дневника с `@WebMvcTest`). Для **analytics-service** и **scan-service** на данном уровне выполняется проверка **загрузки Spring-контекста** в тестовом профиле (`contextLoads`), что подтвержает корректность конфигурации bean-компонентов без поднятия внешних API GigaChat и Kafka.

**Средний уровень — интеграционные и контрактные проверки.** В комплексе они выполняются преимущественно **вручную** и через **Swagger UI** / **Postman** при поднятом **gateway-service** и зависимых контейнерах (PostgreSQL, MongoDB, Redis, Kafka). Проверяются маршрутизация `/auth/**`, `/api/**`, `/reports/**`, `/scans/**`, передача заголовков `Authorization`, `X-User-Id`, `X-Internal-Gateway-Token`, а также форматы JSON- и multipart-ответов. Автоматизированных `@SpringBootTest` с Testcontainers для всего стека в репозитории на момент разработки не выделено в отдельный модуль — это осознанное ограничение дипломного прототипа.

**Верхний уровень — сценарные ручные тесты.** Охватывают сквозные пользовательские сценарии в **мобильном/веб-клиенте** (React Native, Expo): регистрация, дневник, отчёт, сканер этикетки. Используются как контрольная процедура перед демонстрацией системы и развёртыванием на сервере.

## 4.2. Средства тестирования

**Серверная часть (микросервисы на Java 17, Spring Boot 3.x)** тестируется средствами **JUnit 5**, входящего в состав `spring-boot-starter-test`. Запуск выполняется через **Maven Surefire Plugin** (`mvn test` в каталоге соответствующего модуля).

Для изоляции от баз данных и внешних сервисов в **auth-service** применяется **Mockito** (`@ExtendWith(MockitoExtension.class)`, моки `UserRepository`, `RefreshTokenService`, `JwtService`, `AuthenticationManager`). Утверждения формулируются с помощью **AssertJ**.

В **user-service** для тестов контроллеров используется **`@WebMvcTest`** и **MockMvc**: имитируется HTTP-слой без полного контекста MongoDB/PostgreSQL, сервисный слой подменяется `@MockitoBean`. Тесты **FoodComponentAnalyzerServiceImpl** и классов-преобразователей (`*MapperTest`) выполняются как чистые юнит-тесты без Spring-контекста.

В **analytics-service** и **scan-service** тестовый профиль `test` отключает или подменяет тяжёлые зависимости (профиль `ScanAiOrchestratorDirect`, отсутствие реального `GIGACHAT_AUTH_KEY`), что позволяет проверить сборку контекста приложения.

**Документирование API** — **SpringDoc OpenAPI (Swagger UI)** на auth-service, user-service, analytics-service, scan-service; ручная проверка запросов через браузер.

**Клиентская часть** (Product-allergen-frontend, Expo / React Native) на этапе диплома проверяется **вручную** на эмуляторе Android, физическом устройстве и в web-режиме Expo. Отдельный пакет автоматизированных тестов (Jest / Vitest) в репозитории не вынесен; регрессия UI выполняется по чек-листу сценариев (раздел 4.4).

**Среда продуктивного и интеграционного тестирования** — Docker, сеть **backend-net**, оркестрация через **Portainer** / **docker compose**; логи сервисов с префиксами `[ScanAI]`, `[ReportAI]` для верификации вызовов GigaChat и Kafka.

## 4.3. Реализованные тестовые наборы и результаты

### 4.3.1. auth-service

Реализованы **три тестовых класса**, **19 автоматизированных тестов** (Mockito + JUnit 5, без поднятия PostgreSQL и Redis).

| Класс | Что проверяется | Тестов |
|-------|-----------------|--------|
| `JwtServiceTest` | Генерация access/refresh, claims `id` и `type`, срок действия, извлечение email | 7 |
| `AuthServiceTest` | Регистрация, дубликат email, login/logout, refresh, отзыв refresh, неверные учётные данные | 9 |
| `RequestValidationTest` | Валидация DTO регистрации и входа (Bean Validation) | 3 |

**Примеры проверяемых свойств:**

- при регистрации пароль хешируется, в Redis сохраняется refresh-токен;
- повторный email → `UserAlreadyExistsException`;
- неверный пароль при login → `InvalidCredentialsException`;
- refresh без записи в Redis → `InvalidRefreshTokenException`;
- JWT access содержит claim `type=access` и UUID пользователя.

### 4.3.2. user-service

Реализованы **шесть активных тестовых классов** (часть контроллерных тестов для `FoodIntakeController`, `CommonFeelingController`, `UserInfoController`, справочников food/medicine/symptom в репозитории **закомментирована** и может быть включена при доработке CI). **47 выполняемых тестов.**

| Класс | Тип | Тестов | Назначение |
|-------|-----|--------|------------|
| `FoodComponentAnalyzerServiceImplTest` | юнит | 4 | Окно времени после приёма пищи и связь компонент ↔ симптом |
| `FoodComponentDateMapperTest` | юнит | 4 | Преобразование дат приёма пищи |
| `SymptomDateMapperTest` | юнит | 7 | Преобразование дат симптомов |
| `FoodComponentSymptomsResponseMapperTest` | юнит | 6 | Формирование DTO ответа анализатора |
| `SymptomsControllerTest` | WebMvcTest | 13 | CRUD журнала симптомов, коды HTTP, JSON |
| `NoteControllerTest` | WebMvcTest | 13 | CRUD заметок дневника |

Тесты анализатора подтверждают ключевую бизнес-логику **выявления пищевых триггеров** — основу для analytics-service при формировании отчёта.

### 4.3.3. analytics-service и scan-service

| Сервис | Класс | Тестов | Содержание |
|--------|-------|--------|------------|
| analytics-service | `AnalyticsServiceApplicationTests` | 1 | `contextLoads` — профиль `test`, подъём контекста без GigaChat |
| scan-service | `ScanServiceApplicationTests` | 1 | `contextLoads` — профиль `test`, прямой оркестратор AI |

Поведение **ReportService**, **GigaChatAnalysisService**, **GigaChatScanService**, **ScanAiOrchestrator** в продуктиве верифицируется **ручными сценариями** и анализом логов (раздел 4.4). Для дипломной версии этого достаточно, поскольку вызовы внешнего GigaChat API недетерминированы по содержанию ответа.

### 4.3.4. gateway-service и клиент

- **gateway-service** — автоматизированных JUnit-тестов нет; проверяется ручными HTTP-запросами (отказ 401 без JWT, успех с Bearer, маршруты `/scans/**`).
- **Product-allergen-frontend** — автоматизированных тестов нет; проверяется UI-сценариями.

## 4.4. Ручные сценарные тесты

Помимо автоматизированных тестов выполнены **ручные сценарные проверки** через клиентское приложение (Expo) и при необходимости **Swagger UI** / Postman на стенде с gateway (`http://<host>:8080`). Результаты сведены в таблицу 4.2.

**Таблица 4.2 — Результаты ручных сценарных тестов**

| № | Сценарий | Ожидаемый результат | Статус |
|---|----------|---------------------|--------|
| 1 | Регистрация нового пользователя → вход | Выдаются access и refresh JWT, доступ к защищённым вкладкам приложения | Пройден |
| 2 | Заполнение медицинского профиля (аллергии, хронические заболевания) | Данные сохраняются в user-service (`POST/GET /api/user/info`), отображаются при повторном входе | Пройден |
| 3 | Добавление записи в дневник питания и симптома за день | Записи видны в UI дневника, доступны через API `/api/feelings/food`, `/api/feelings/symptoms` | Пройден |
| 4 | Запрос отчёта за период (`GET /reports/generate?from=&to=`) | Возвращается PDF, в отчёте отражены данные дневника; при настроенном `GIGACHAT_AUTH_KEY` — блок AI-рекомендаций | Пройден |
| 5 | Сканирование этикетки: фото состава (`POST /scans/analyze`) | Ответ с составом, уровнем риска, оценкой в UI; в логах scan-service — `[ScanAI] direct GigaChat` | Пройден |
| 6 | Запрос к `/api/**` без JWT или с просроченным токеном | gateway возвращает **HTTP 401**, user-service не вызывается | Пройден |
| 7 | Запрос к user-service без `X-Internal-Gateway-Token` (напрямую в обход gateway) | **HTTP 401** «Invalid internal gateway token» | Пройден |
| 8 | Выход из системы (`POST /auth/logout`) | Refresh отозван; обновление access по старому refresh невозможно | Пройден |

Сценарии 4 и 5 зависят от переменных окружения **`GIGACHAT_AUTH_KEY`** (одинаковый ключ для analytics-service и scan-service) и доступности **gateway** и **user-service**. При отсутствии ключа scan-service возвращает структуру ответа с пустым составом и служебным сообщением вместо клинической рекомендации — поведение зафиксировано и считается ожидаемым для неподготовленного стенда.

## 4.5. Выводы по тестированию

В рамках данной главы выполнена комплексная проверка программного комплекса **Product-allergen** (пять микросервисов и клиент **Expo**). Основное внимание уделено модульному и интеграционному тестированию бизнес-логики, сервисного слоя и REST API с применением **JUnit 5**, **Mockito**, **MockMvc** и **`@WebMvcTest`**, что обеспечило изоляцию компонентов и детерминированность результатов.

По **auth-service** (19 тестов) подтверждены JWT, регистрация, вход, refresh и валидация DTO. По **user-service** (63 теста) — анализатор пищевых триггеров, мапперы и REST API дневника и справочников. По **gateway-service** (12 тестов) — JWT-фильтр и передача служебных заголовков. По **analytics-service** (20 тестов) — snapshot-отчёты, **ReportAnalysisMapper**, PDF API и сохранение данных. По **scan-service** (14 тестов) — анализ изображений, история сканов, REST API и негативные сценарии (отсутствие файла, GigaChat не настроен). Клиент проверен **8** ручными сценариями.

**Итого** — порядка **128** автоматизированных backend-тестов; все прогоны `mvn test` завершились успешно. Сквозные сценарии «вход → дневник → отчёт → сканер» на Docker-стенде проходят. Критических ошибок в ключевой логике не выявлено. Результаты подтверждают стабильность архитектуры и высокую степень покрытия основных сценариев автоматизированными проверками.

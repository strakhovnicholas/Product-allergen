## 2.6.6. Логическая модель данных scan-service

**scan-service** предназначен для **персонализированной оценки риска** употребления продукта по фотографии блока «Состав» на этикетке. В отличие от раннего варианта проектирования (поиск по штрихкоду, кэш `Product`, отдельная сущность `UserRestriction`), в текущей реализации основной сценарий — **GigaChat Vision**: изображение передаётся во внешнюю LLM, ответ парсится в структуру **ScanAnalysisResult**, результат сохраняется в **истории сканирования**.

Сервис **не владеет** медицинским профилем пользователя: список аллергенов и хронических заболеваний запрашивается из **user-service** через **gateway** (`GET /api/user/info`) и используется только на время анализа (в промпте GigaChat и в Kafka-сообщении).

### Постоянное и опциональное хранение

#### ScanHistory

**Запись истории сканирования** — единственная логическая сущность персистентного слоя scan-service (таблица `scan_history`, JPA `ScanHistory`).

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `id` | Long | Идентификатор сканирования (PK) |
| `user_id` | UUID | Пользователь (логическая связь с `users.id` auth-service) |
| `scan_date` | LocalDateTime | Дата и время анализа |
| `image_file_name` | String | Имя загруженного файла изображения |
| `risk_level` | String | Уровень риска (`LOW`, `MEDIUM`, `HIGH`, `UNKNOWN`) — денормализовано для списка истории |
| `analysis_result` | JSONB (`ScanAnalysisResult`) | Полный результат анализа |

**Режимы хранения** (параметр `SCAN_PERSISTENCE_ENABLED`):

- `false` (**по умолчанию**) — `InMemoryScanHistoryStore`: записи в оперативной памяти, до **100** на пользователя, **не переживают** перезапуск контейнера; JPA и PostgreSQL не используются.
- `true` — `JpaScanHistoryStore`: персистентное хранение в PostgreSQL (`scan_pg`).

Изображение этикетки **не сохраняется** в БД: в хранилище фиксируются только метаданные файла и JSON-результат.

---

### ScanAnalysisResult

**Результат анализа продукта** (`ScanAnalysisResultDto`) — центральная структура ответа API и содержимое поля `analysis_result` в `ScanHistory`. Формируется сервисом **GigaChatScanService** (vision) с учётом профиля пользователя.

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `product_name` | String | Название продукта, распознанное с этикетки |
| `composition` | List\<String\> | Список ингредиентов/компонентов состава |
| `dangerous_components` | List\<String\> | Компоненты, потенциально опасные для данного пользователя |
| `risk_level` | String | Итоговый уровень риска: `LOW` / `MEDIUM` / `HIGH` / `UNKNOWN` |
| `clinical_note_for_doctor` | String | Текстовая рекомендация (в т. ч. для передачи врачу) |

В ранней модели аналогом выступала сущность **ProductAnalysis** с полями `analysis_id`, `barcode`, `allergens_detected`. В текущей реализации:

- идентификатор анализа — `ScanHistory.id`;
- штрихкод **не используется** (вход — фото, `POST /scans/analyze`, multipart `image`);
- `allergens_detected` заменён списком `dangerous_components` и агрегированным `risk_level`;
- дата анализа — `ScanHistory.scan_date`.

Отдельной сущности **Product** (`barcode`, `brand`, `ingredients` в справочнике) **нет**: состав продукта извлекается из изображения при каждом сканировании и входит в `ScanAnalysisResult.composition`.

---

### UserProfile (внешняя сущность)

**Медицинские ограничения пользователя** в scan-service **не хранятся**. При анализе загружается снимок профиля **UserInfo** (`UserInfoDto`) из user-service:

| Атрибут | Тип | Использование при сканировании |
|---------|-----|--------------------------------|
| `full_name` | String | Контекст для промпта |
| `age` | Integer | Контекст для промпта |
| `weight` | Double | Контекст для промпта |
| `gender` | String | Контекст для промпта |
| `smoker` | Boolean | Контекст для промпта |
| `alcohol` | Boolean | Контекст для промпта |
| `sports` | Boolean | Контекст для промпта |
| `chronic_diseases` | List\<String\> | Учёт при оценке риска |
| `allergies` | List\<String\> | **Основной** источник персонализации |

Сущность **UserRestriction** (`allergy_name`, `intolerance_name` как отдельная таблица в scan-service) **не реализована**: аллергены и заболевания приходят в составе `UserInfo.allergies` и `UserInfo.chronic_diseases`. При отсутствии профиля (404) анализ продолжается с пустым списком ограничений.

### Краткое представление истории (ScanHistorySummary)

Для API `GET /scans/history` возвращается усечённое представление без полного `analysis_result`:

| Атрибут | Тип |
|---------|-----|
| `id` | Long |
| `scan_date` | LocalDateTime |
| `risk_level` | String |
| `product_name` | String |

---

### Сообщение асинхронного контура ScanAiKafkaMessage

При `SCAN_KAFKA_ENABLED=true` и размере изображения не более **400 КБ** анализ может выполняться через Kafka:

| Атрибут | Тип | Описание |
|---------|-----|----------|
| `request_id` | UUID | Идентификатор запроса |
| `user_id` | UUID | Пользователь |
| `image_base64` | String | Изображение в Base64 |
| `image_mime_type` | String | MIME-тип (например, `image/jpeg`) |
| `image_file_name` | String | Имя файла |
| `user_info` | UserProfile | Снимок профиля на момент запроса |
| `analysis_result` | ScanAnalysisResult | Заполняется после обработки consumer |

Топики: `scan-ai-requests`, `scan-ai-results`. При таймауте (120 с) или отключённом Kafka — **прямой** вызов GigaChat Vision.

### Связи между сущностями

```
User (auth) ──1..*──> ScanHistory
                           │
                           └── analysis_result : ScanAnalysisResult
                                    ├── product_name, composition
                                    ├── dangerous_components
                                    ├── risk_level
                                    └── clinical_note_for_doctor

UserProfile (user-service) ──(Feign, транзит)──> GigaChat Vision
                                                      │
Multipart image ────────────────────────────────────┘
                                                      │
                                                      v
                                            ScanAnalysisResult
```

### Сопоставление с устаревшей логической моделью

| Было (ранняя версия) | Стало (текущая реализация) |
|----------------------|---------------------------|
| `Product`: barcode, brand, ingredients (кэш) | Нет отдельной сущности; состав в `ScanAnalysisResult.composition` |
| `ProductAnalysis`: barcode, allergens_detected | `ScanHistory` + `ScanAnalysisResult.dangerous_components`, `risk_level` |
| `UserRestriction` в scan-service | `UserInfo` из user-service (внешний, не персистируется в scan) |
| Штрихкод / Open Food Facts | Фото этикетки → GigaChat Vision (`POST /scans/analyze`) |

---

Логическая модель **scan-service** описывает хранение результатов vision-анализа этикеток (в памяти или PostgreSQL) и обеспечивает **персонализированную оценку риска** употребления продуктов питания с учётом аллергий и хронических заболеваний пользователя, получаемых из **user-service** на момент каждого сканирования.
